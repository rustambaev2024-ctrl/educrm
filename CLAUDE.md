## 8 столпов UI — весь интерфейс строится по ним
Активные скилы: `frontend-design`, `design-system`, `shadcn`. Стек: TanStack Start + Tailwind v4 + shadcn/ui (new-york, radix, lucide). Всегда используй семантические токены (`bg-primary`, `text-muted-foreground`), `gap-*` вместо `space-y-*`, `size-*` вместо `w-* h-*`.

1. **Микроанимации и переходы.** Каждое действие имеет плавный отклик 150–300ms: карточки fade-in, панели выезжают, кнопка при нажатии «проваливается». Анимации shadcn Dialog/Sheet использовать как есть. Уважать `prefers-reduced-motion`.
2. **Типографика с иерархией.** С первого взгляда ясно: главное / второстепенное / подсказка. Разные размеры и веса (light/regular/semibold/bold), правильный line-height. Не делать всё одним размером.
3. **Состояния каждого элемента.** Минимум 5 состояний: обычное, hover, active, disabled, loading. Пользователь всегда понимает, можно ли кликнуть и что происходит.
4. **Пустые состояния.** Пустой список = компонент `Empty`: иконка + понятный текст («У вас пока нет студентов») + кнопка действия. Никогда просто белый экран.
5. **Обратная связь на каждое действие.** Клик → спиннер/«Сохраняем…» → `sonner` toast: зелёный «Сохранено» или красный с конкретной причиной. Ошибки прокидывают детали через `apiErrorMessage`, не голое «Xatolik».
6. **Детали для внимательного взгляда.** Аватар с инициалами — цвет детерминирован по имени, иконки выровнены с текстом (`data-icon`), чередование строк таблицы, тонкая цветная черта слева у активного пункта меню.
7. **Осмысленные цвета, не декоративные.** Красный = только опасность/удаление, зелёный = успех/активность, жёлтый = предупреждение, серый = неактивное. Цвет несёт информацию. Никаких `bg-blue-500` «потому что синий».
8. **Отзывчивость под контекст.** Не сжатый десктоп: на мобиле таблица → карточки, боковое меню → нижняя навигация, тач-таргеты ≥44px, модалки открываются снизу как `Drawer`/`Sheet`. student/ и parent/ порталы — mobile-first (`MobileLayout`).

### Аудит автоматических функций + биллинга (НЕ ЗАКОММИЧЕНО, ждёт одобрения)
Отчёт для владельца (без техтерминов, визуальный):
https://claude.ai/code/artifact/a7fbb648-ccb5-4f6d-8686-7efaaae282b1
Аудит корректности данных (раньше в этой же сессии):
https://claude.ai/code/artifact/b3531984-4d45-4e0b-935f-91e47c86dc01

**Повод:** клиенты — «в воскресенье списались деньги, уроков не было ни у кого»
+ «система то работает, то нет». Владелец сформулировал правило: деньги
списываются за каждое занятие, КРОМЕ отменённого, перенесённого и
уважительной причины.

**Корневая причина списаний в пустоту.** `daily_lesson_charge` брал деньги по
`Group.schedule`, не проверяя существование `Lesson`: условие было
`if lesson and lesson.status == "cancelled"`, то есть `lesson is None`
не останавливало списание. А `generate_lessons_for_group_sync` учитывает
`start_date`, `end_date`, наличие `start` у слота и конечный горизонт —
биллинг не учитывал ничего. Каждое расхождение = списание в день без урока,
причём с `lesson_id = NULL`, из-за чего сигнал `refund_charge_when_marked_excused`
(ищет по `lesson_id`) не мог его вернуть даже вручную.
Главный практический источник: **слот расписания без времени начала** —
урок не создаётся никогда, деньги снимаются каждую неделю.

**Ключевые правки бэкенда:**
- `charge_groups_for_day()` вынесена из `_charge_all_tenants` — до этого
  расчёт списаний не был покрыт НИ ОДНИМ тестом (обход тенантов не работает
  на SQLite). Теперь `tests/test_billing_requires_lesson.py`, 8 тестов.
- Списание требует реального `Lesson`; `cancelled` И `rescheduled` пропускаются;
  отсутствие урока в учебный день пишется в `logger.warning`, а не молчит.
- **Ключ идемпотентности — урок, а не `created_at__date=today`.** Старый ключ
  сравнивал расчётный день с календарным днём записи, причём `created_at__date`
  считается в Asia/Tashkent, а `today` приходил из `date.today()` (UTC
  контейнера, TZ в Dockerfile не задан). Тест доказал двойное списание при
  повторном прогоне.
- `refund_lesson_charges()` в `finance/services.py` — общий возврат для трёх
  поводов (отмена / перенос / excused). Отмена и перенос деньги НЕ возвращали
  вообще: за перенесённый урок платили дважды.
- `resync_lessons_for_group` исключает `rescheduled_from__isnull=False` —
  правка расписания молча стирала урок, созданный переносом (у старого
  оставалась метка «перенесён» и указатель в NULL).
- Перенос: запрещён в прошлое, на занятое время (409) и для `conducted`;
  посещаемость нельзя ставить на `rescheduled`; добавлено
  `NotificationService.on_lesson_rescheduled` (раньше не уведомляли никого).
- `trigger_daily_charge` вызывал `daily_lesson_charge()` → обход ВСЕХ тенантов
  синхронно в HTTP-запросе. Теперь только текущая схема, под замком по схеме.
- `reverse_payment`: `select_for_update` + проверка повтора ВНУТРИ (была только
  во вьюхе и в сигнале — не атомарно, три источника отмены).
- `mark_overdue_homework` **не обходил тенанты вообще** → «просрочено» не
  проставлялось никому ни разу. Тест на неё проходил именно поэтому; вынесена
  `mark_overdue_in_current_schema()`, тест переписан.
- `send_debtor_sms` фильтровал `wallet_balance__lt=0 AND status="active"`, а
  должнику статус автоматически ставится `debtor` → SMS не уходили почти никому.
- `send_trial_lesson_sms`: окно 20–28 ч = только 05:00–13:00 завтра.
- `lesson_reminder` / `trial_lesson_reminder`: окно 10 мин при шаге 30 мин →
  слепая зона, доходило до ~трети. `REMINDER_SCAN_MINUTES = 35` + `_already_notified`.
- `update_debtor_statuses` чинил только `debtor → active`, обратного не было.
- 5 глухих `except: pass` в `coins/signals.py` → `logger.exception`.
- 6 мест считали дату через `date.today()`/`timezone.now().date()` → `localdate()`.
- `apps/core/definitions.py` — единое место для наборов статусов и типов
  операций (+ `wallet_delta`), зеркало `src/lib/data/definitions.ts`,
  паритет сторон стережёт `tests/test_definitions_parity.py`.

**Возврат уже списанного:** `python manage.py refund_phantom_charges`
(dry-run по умолчанию, `--apply` возвращает). Опознаёт по двум признакам
сразу — `lesson__isnull=True` И `comment__startswith="Daily lesson charge"`,

**Ожидаемый эффект после деплоя:** сборы станут меньше на сумму бывших
фантомных списаний. Если календарь группы не заполнен — деньги не спишутся,

**Владельцу проверить руками:** у каждой группы в расписании должно быть
