# ship-pr

Стандартный путь изменения от рабочей копии до прод-Railway в этом репозитории.
Именно эта последовательность использовалась во всех PR #9–#18 — воспроизводится
здесь дословно, чтобы ни один шаг не потерялся между сессиями.

Каждый шаг ниже — обязательный чек-пункт. Не пропускать и не переставлять
местами без явной причины (например, шаг с CI можно пропустить только если
пользователь явно сказал не ждать проверки).

## 1. Убедиться, что есть что коммитить, и это безопасно

```bash
git status --short
```

Если есть незакоммиченные изменения, не относящиеся к текущей задаче —
остановиться и спросить пользователя, а не тащить их в этот PR молча.

## 2. Ветка

Только если сейчас на `master`/`main`:

```bash
git checkout -b <type>/<short-topic>
```

`type` — `feat`, `fix`, `docs`, `refactor` — по смыслу изменений.

## 3. Коммит

```bash
git add <конкретные файлы, НЕ -A вслепую>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <короткое summary — что и зачем, не "что изменено">

<опционально: 1-3 абзаца контекста — какую проблему решает, что было раньше>

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
)"
```

Сообщение объясняет **почему**, а не построчно перечисляет диф.

## 4. Прогнать локальные гейты ДО пуша

Что применимо к изменённым файлам:

```bash
# backend
cd backend && python -m flake8 <изменённые .py>
DJANGO_SETTINGS_MODULE=config.settings.test python -m pytest tests -q

# frontend
npm run build
```

Если что-то падает — чинить здесь, не полагаться на CI как на единственный гейт.

## 5. Push и PR

```bash
git push -u origin <branch>
gh pr create --title "<type>: <короткий заголовок>" --body "$(cat <<'EOF'
## Summary
- <буллет 1>
- <буллет 2>

## Test plan
- [x] <что реально проверено>
- [ ] <что осталось проверить руками>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

## 6. Дождаться CI (не мержить вслепую)

```bash
gh pr checks <номер>
```

Опрашивать с паузами (10–20 сек), пока не исчезнут `pending`. Если что-то
`fail` — читать лог джобы (`gh run view --log-failed`), чинить, пушить fix
в ту же ветку, возвращаться к этому шагу.

## 7. Merge и синхронизация локального master

```bash
gh pr merge <номер> --merge --delete-branch
git checkout master
git fetch --prune
git reset --hard origin/master
```

## 8. Проверить прод

Railway обычно деплоит автоматически на push в `master`. Подтвердить не
догадкой, а фактом:

```bash
# статус последнего деплоя (MCP railway: get-status / list-deployments)
# или напрямую:
railway ssh --service educrm -- python manage.py showmigrations <затронутые apps>
curl -s -o /dev/null -w "HTTP %{http_code}\n" https://<прод-домен>/api/v1/health/
```

Если менялась модель — здесь же смотреть, что нужная миграция помечена `[X]`
на самом проде (не только локально/в CI-SQLite — под тестами `apps.tenants`
вообще выключен, см. `config/settings/test.py`).

## Что НЕ делает этот skill

- Не форс-пушит и не трогает историю — только обычный merge-commit.
- Не мержит без прохождения CI (кроме явного запроса пользователя).
- Не коммитит `.env`/секреты — если `git status` показывает такой файл,
  остановиться и спросить.
