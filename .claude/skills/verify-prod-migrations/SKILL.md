# verify-prod-migrations

Этот проект уже пережил один ложный тревожный сигнал (казалось, что на проде
не хватает колонки `sms_enabled`) и держит открытым риск того, что release-фаза
Railway когда-нибудь не выполнит `migrate` полностью. Прямая проверка через SSH
занимает секунды и снимает вопрос окончательно — вместо гадания по логам или
воспроизведения локально (локальная БД — НЕ прод, дефолты в
`backend/config/settings/base.py` указывают на `localhost`, легко перепутать).

## Как проверять

1. Определить сервис и apps, которые нужно проверить:

```bash
railway status
```

Прод-проект — `pleasing-trust`, сервис бэкенда — `educrm` (не путать с
`rare-elegance` — это фронтенд).

2. Прогнать `showmigrations` по всем приложениям с открытыми миграциями
   (или конкретно по тем, что менялись в последнем PR):

```bash
railway ssh --service educrm -- python manage.py showmigrations
```

Для точечной проверки после конкретного PR — список приложений, которые он
трогал:

```bash
railway ssh --service educrm -- python manage.py showmigrations tenants students finance
```

3. Каждая строка должна быть `[X]`. Любая `[ ]` — миграция создана в коде, но
   не применена на проде. Это боевой инцидент, а не техдолг:
   - Прочитать, что делает непринятая миграция (`cat backend/apps/<app>/migrations/000N_*.py`) —
     убедиться, что она безопасна для применения на живых данных (не дропает
     колонки с данными, не блокирует таблицу надолго).
   - Только после этого — `railway ssh --service educrm -- python manage.py migrate <app>`.
   - Никогда не запускать `migrate` без предварительного показа пользователю,
     какая именно миграция не применена и что она делает — прод-БД **не имеет
     бэкапов** (PITR выключен, см. память `educrm-railway-backups-missing`).

4. Живая проверка на уровне HTTP (быстрая сверка, что API вообще не 500-ит):

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" https://<прод-домен>/api/v1/health/
```

## Частые ловушки

- `railway run` выполняет команду **локально** с прод-переменными окружения —
  но `POSTGRES_HOST` на Railway обычно внутренний (`postgres.railway.internal`),
  недоступный с локальной машины напрямую. Для доступа к самой прод-БД нужен
  именно `railway ssh` (выполняется внутри контейнера), не `railway run`.
- `config/settings/test.py` полностью выключает `apps.tenants` и
  `django_tenants` для прогона pytest под SQLite — зелёные тесты **не**
  доказывают, что миграции тенантов накатятся на Postgres. Эта проверка — тот
  недостающий шаг, который тесты в CI не покрывают.
