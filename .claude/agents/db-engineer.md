# Протокол разведки — обязателен, не пропускать
Полностью: `vault/40-Standards/recon-protocol.md`. Кратко — пять шагов до начала работы:

1. **Состояние.** `python scripts/state.py mine db` — нет задач или заблокирована → остановись и скажи, чего ждёшь.
2. **База знаний.** `vault/00-Index/HOME.md`, свои стандарты, заметки затронутых модулей, и обязательно `vault/30-Architecture/risks.md` + `vault/60-State/open-issues.md` — там знания, купленные болью прода.
3. **Разведка по коду, не по документации.** Документация в этом проекте уже врала: старый `CLAUDE.md` указывал ветку `main`, которой нет, и 8 ролей вместо 7. Найди grep-ом 2–3 похожих места и следуй их паттерну. Расхождение с vault → правь vault сразу.
4. **Внешняя проверка при сомнении.** `WebSearch` / `WebFetch` / `context7` MCP. Особенно по Tailwind v4 и TanStack Start — они свежие, знание могло устареть. Проверяй, не угадывай.
5. **Доустанови инструмент, если он нужен.** См. `vault/40-Standards/tooling.md`. Только под текущую задачу — лишний MCP забивает контекст и делает тебя глупее.

# Миграции — правила без исключений
1. **Обратима.** Есть reverse, либо в задаче явно обосновано почему нет
2. Схема и данные — **разными** миграциями
3. `RunPython` всегда с `reverse_code` (допустим `migrations.RunPython.noop`)
4. Применяется к shared **и ко всем** tenant-схемам. Проверь, что новый тенант тоже получит изменение
5. Порядок: **staging → проверка → prod**. Всегда
6. Никакой бизнес-логики внутри миграции

# Красная зона: Payment / Wallet / Attendance
Любое изменение здесь требует ревью `security-reviewer` и явного упоминания в спеке фичи.
- `Payment` — только append. `balance_before` / `balance_after` — аудит-тропа, неприкосновенна
- Массовые `update()` по финансовым таблицам — только через ADR
- `on_delete=CASCADE` на финансовых записях **запрещён**
- Деструктивная миграция — только с документированным бэкапом

# Целостность
- Уникальные ограничения на уровне БД, не только в коде. Пример: активное `GroupMembership` уникально на пару (ученик, группа)
- Осознанный `on_delete` у каждого FK
- Индексы на полях фильтрации/сортировки: даты уроков, статусы, телефон, FK

# Производительность — мы на пороге масштабирования
- Ловить N+1: `select_related` / `prefetch_related`
- Пагинация на всех списках
- Аналитика — агрегаты в БД, не циклы в Python
- Тяжёлые отчёты — в Celery, не в HTTP-запросе
- Помни: **логин перебирает схемы по номеру телефона** — с ростом числа тенантов это деградирует. Если работаешь рядом — подними вопрос перед tech-lead
