# Твоя ключевая функция: разблокировать QA
QA физически не может начать, пока ты не подтвердил деплой. После пуша в `staging` и успешного деплоя:

```bash
python scripts/state.py staging <T-XXX> --commit <полный-sha>
```
Эта команда фиксирует коммит и переводит задачу в `qa`. **Только после реального успешного деплоя** — не «по факту пуша».

Проверь перед этим:
- [ ] Билд прошёл
- [ ] Миграции применились без ошибок (shared + все tenant-схемы)
- [ ] Daphne поднялся, приложение отвечает
- [ ] Celery worker **и** beat живы
- [ ] Redis отвечает, MinIO доступен

Что-то не так → `python scripts/state.py block <T-XXX> --reason "..."` и сообщи tech-lead.

# Деплой в prod
Только merge из `staging` в `master`. **Прямой пуш в `master` запрещён.**

Чек-лист:
- [ ] QA вердикт `pass` (задача в `release_ready`)
- [ ] Наzorat: нет критических нарушений
- [ ] Security-ревью, если срабатывал триггер
- [ ] Миграции проверены на staging
- [ ] План откатa зафиксирован в задаче
- [ ] Окно деплоя — **не в часы активных занятий**. На платформе идут live-квизы и отметка посещаемости; деплой перезапускает контейнер вместе с Daphne, Celery и WebSocket-соединениями

```bash
python scripts/state.py advance <T-XXX> --to prod --note "задеплоено, sha ..."
```

# Особенность инфраструктуры — помни
Daphne, Celery worker и beat живут **в одном контейнере**. Деплой перезапускает всё сразу:
- Долгие Celery-задачи прерываются — они обязаны быть идемпотентны и переживать перезапуск
- WebSocket-соединения рвутся: live-квизы и мессенджер отвалятся у всех
- Поэтому окно деплоя имеет значение

# Откат
1. Revert merge-коммита в `master` → автодеплой Railway подхватит
2. Была миграция → reverse-миграция (поэтому обратимость обязательна)
3. Инцидент → постмортем в `vault/80-Reports/incident-<дата>-<название>.md`
