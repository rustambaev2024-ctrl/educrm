# Фича F-002: Полный аудит функциональности платформы — исправление критических дефектов

- **Автор спеки:** tech-lead
- **Дата:** 2026-07-29
- **Затронутые модули:** homework, grades, coins, finance, students, quizzes, chat, accounts, staff, courses, lessons, reports
- **Затронутые роли:** все 7 — superadmin, director, branch_admin, teacher, support_teacher, student, parent

## 1. Задача

Владелец платформы попросил через `/tl` полный QA-аудит всей функциональности — без конкретных багов, только общее ощущение «что-то не так». Подняты параллельно `qa-engineer` (полный тест-план по всем модулям и ролям), `backend-dev` + `db-engineer` (причины трёх открытых жалоб И-1/И-2/И-3 из `open-issues.md`) и `security-reviewer` (красные зоны: деньги, тенант, PII, права).

Итог: **5 blocker, ~15 critical, ~18 major, ~7 minor** дефектов. Четыре из них — активная утечка/повреждение данных между учебными центрами или PII несовершеннолетних, эксплуатируемые одним HTTP-запросом из браузера обычного пользователя. Security-reviewer вынес вердикт `REJECTED` на переход в staging для новых фич до устранения S-1/S-2/S-3/S-4/S-5.

Успехом считаем: устранены все 5 blocker + перечисленные ниже critical денежно/тенантно/PII-значимые дефекты, security-reviewer снимает REJECTED, QA прогоняет регресс красных зон и подтверждает.

Причины И-1/И-2/И-3 уже найдены и вписаны в `vault/60-State/open-issues.md`. Полный список всех находок с файлами/строками — в risks.md R-13…R-25 и в отчётах сессии (не сохранены отдельным файлом, доступны через журнал этой задачи).

## 2. Что НЕ входит

- **Major/minor дефекты** (i18n-пробелы, кеш отчётов на 5 минут, лидерборд без фильтра филиала, асимметрия лимитов магазина и т.д.) — зафиксированы в R-25 и открыты для отдельного `/tl`-захода, в эту фичу не включены. Объём полного списка (18 major + 7 minor) требует отдельной приоритизации с владельцем продукта (часть — не баги, а нерешённые продуктовые вопросы, напр. m-4, m-7).
- **T-001…T-007 (F-001, ребренд/тёмная тема)** — независимая фича, не трогаем.
- **Визуальный регресс тёмной темы на 7 порталах** — предмет T-006, ждёт своих зависимостей отдельно.
- **R-1 (Celery worker/beat дублирование), R-2 (полное решение user enumeration), R-4 (Redis db/0), R-5 (media на ephemeral-диске), R-7 (Daphne single-process), R-8 (98 проверок роли)** — существующие риски, не новые находки, чинятся отдельными задачами вне этой фичи.
- Продуктовые вопросы без единственно верного ответа (лимиты магазина m-4, доступ support_teacher к экзаменам m-7) — выносятся человеку отдельно, не решаем за него.

## 4. Влияние на слои

- **Дизайн:** не затронут — все находки бэкендные (авторизация, бизнес-логика, изоляция).
- **Frontend:** не затронут в рамках blocker-тира; возможны точечные правки обработки 403 там, где сейчас фронт слепо доверяет 200-ответу (M-6 из отчёта QA, follow-up).
- **Backend / API:** контракт не ломается для легитимных сценариев — все правки сужают несанкционированный доступ, а не убирают функциональность. - **Реалтайм (Channels):** R-19 — WS-слой квиза переписывается на паттерн `chat/auth_middleware.py` (схема только из JWT, группа с префиксом схемы).

## 9. T-011 — изменения схемы БД (db-engineer, 2026-07-29)

### 9.1 Что меняется

| Модель.поле | Было | Стало | Миграция |
|---|---|---|---|
| `finance.Payment.wallet` | `CASCADE` | `PROTECT` | `finance/0008_payment_wallet_protect.py` |
| `coins.CoinTransaction.wallet` | `CASCADE` | `PROTECT` | `coins/0003_cointransaction_wallet_protect.py` |

Разорванные цепочки уничтожения:
- `Student` → (CASCADE) `Wallet` → (~~CASCADE~~ **PROTECT**) `Payment`
- `Student` → (CASCADE) `CoinWallet` → (~~CASCADE~~ **PROTECT**) `CoinTransaction`

Ничего больше не тронуто: `Wallet.student` и `CoinWallet.student` остаются `CASCADE`
намеренно — `PROTECT` на верхнем звене цепочки достаточно, чтобы `Collector` поднял
`ProtectedError`, и это меньшее изменение поверхности. `Payment.student` остаётся
`SET_NULL` (уже был). Логика начисления/списания не менялась ни строкой.

### 9.2 Обратимость и стоимость применения

`on_delete` — поведение уровня Django, **не уровня PostgreSQL**. `db_constraint` не менялся,
поэтому обе миграции — no-op на уровне SQL, подтверждено:

```
$ python manage.py sqlmigrate finance 0008   →  BEGIN; -- (no-op) COMMIT;
$ python manage.py sqlmigrate coins   0003   →  BEGIN; -- (no-op) COMMIT;
```

Следствия: нулевое время применения, **никаких блокировок таблиц**, объём данных не важен.
Откат — стандартный Django, такой же no-op:

```bash
python manage.py migrate_schemas --tenant finance 0007
python manage.py migrate_schemas --tenant coins   0002
```

Обе миграции — в `TENANT_APPS`, применяются `migrate_schemas` ко всем схемам тенантов;
новый тенант получает их автоматически при создании схемы. `public` не затронута.

### 9.3 Риски

1. **Ожидаемое (не баг):** `DELETE /api/v1/students/<id>/` для ученика с историей платежей
   или монет перестаёт физически удалять запись. Текущий `students/views.py:190-207`
   уже ловит исключение и делает fallback — `status='archived'` + `user.is_active=False`,
   ответ **200** с двуязычным «Архивирован (удаление невозможно)». То есть после миграции
   поведение прода не падает 500, а деградирует в мягкое архивирование само по себе.
   `ProtectedError` поднимается `Collector`-ом на стадии сбора связей, **до первого DELETE**,
   поэтому `transaction.atomic` не ломается и последующий `student.save()` в except проходит.
   Это ключевой факт для T-012.
2. **Остаточная дыра, которую закрывает T-012:** ученик без единого платежа и без монетных
   транзакций удаляется физически по-прежнему — вместе с `StudentDocument` (PII),
   посещаемостью и оценками. `PROTECT` необходим, но недостаточен; soft-delete обязателен.
3. Широкий `except Exception` в `destroy()` теперь становится штатным путём выполнения —
   T-012 должен заменить его явным `except ProtectedError`, иначе реальные ошибки БД
   продолжат маскироваться под «архивирован».
4. Побочный положительный эффект: удаление `User` ученика напрямую тоже блокируется
   (`User` → `Student` → `Wallet` → `Payment`).

### 9.4 Порядок применения

1. Прогнать pre-flight SQL (9.5) на **staging** → посмотреть метрики.
2. Применить миграции на staging, регресс QA: удаление ученика **с** платежами → 200 «архивирован»,
   удаление ученика **без** платежей → 204 (пока T-012 не закрыт), создание платежа/начисление монет
   работают без изменений, `daily_lesson_charge` отрабатывает.
3. Прогнать тот же pre-flight SQL на **prod** — только чтение, до применения. Ненулевые
   значения метрик `3_*` разбирать до миграции.
4. Применить на prod: `python manage.py migrate_schemas --tenant`.
5. План отката — 9.2. Бэкап не требуется: миграции не выполняют DDL и не трогают данные.

### 9.5 Pre-flight SQL — прогнать по всем схемам тенантов до применения

READ-ONLY, оборачивается в `BEGIN … ROLLBACK`, сам итерирует схемы.

```sql
BEGIN;

CREATE TEMP TABLE r21_check (schema_name text, metric text, cnt bigint) ON COMMIT DROP;

DO $do$
DECLARE s text;
BEGIN
    FOR s IN
        SELECT n.nspname FROM pg_namespace n
         WHERE n.nspname NOT IN ('public', 'information_schema')
           AND n.nspname NOT LIKE 'pg\_%'
           AND EXISTS (SELECT 1 FROM pg_class c
                        WHERE c.relnamespace = n.oid
                          AND c.relname = 'finance_payment' AND c.relkind = 'r')
         ORDER BY n.nspname
    LOOP
        EXECUTE format($q$
            INSERT INTO r21_check (schema_name, metric, cnt)
            -- 0. объём аудит-тропы, которая сейчас под угрозой
            SELECT %1$L, '0_payments_total', count(*) FROM %1$I.finance_payment
            UNION ALL
            SELECT %1$L, '0_coin_tx_total', count(*) FROM %1$I.coins_transaction
            -- 1. МАСШТАБ PROTECT: сколько учеников перестанут удаляться
            UNION ALL
            SELECT %1$L, '1_students_blocked_by_payment', count(DISTINCT w.student_id)
              FROM %1$I.finance_wallet w JOIN %1$I.finance_payment p ON p.wallet_id = w.id
            UNION ALL
            SELECT %1$L, '1_students_blocked_by_cointx', count(DISTINCT cw.student_id)
              FROM %1$I.coins_wallet cw JOIN %1$I.coins_transaction t ON t.wallet_id = cw.id
            -- 2. ОСТАТОЧНАЯ ДЫРА: кого PROTECT не защитит (аргумент за T-012)
            UNION ALL
            SELECT %1$L, '2_students_still_deletable', count(*)
              FROM %1$I.students_student st
             WHERE NOT EXISTS (SELECT 1 FROM %1$I.finance_wallet w
                                 JOIN %1$I.finance_payment p ON p.wallet_id = w.id
                                WHERE w.student_id = st.id)
               AND NOT EXISTS (SELECT 1 FROM %1$I.coins_wallet cw
                                 JOIN %1$I.coins_transaction t ON t.wallet_id = cw.id
                                WHERE cw.student_id = st.id)
            -- 3. АНОМАЛИИ: связь уже потеряна / PROTECT не сработает
            UNION ALL
            SELECT %1$L, '3_payments_wallet_null', count(*)
              FROM %1$I.finance_payment WHERE wallet_id IS NULL
            UNION ALL
            SELECT %1$L, '3_payments_wallet_null_student_null', count(*)
              FROM %1$I.finance_payment
             WHERE wallet_id IS NULL AND student_id IS NULL
               AND payment_type IN ('top_up','charge','discount','refund',
                                    'manual_charge','manual_top_up')
            UNION ALL
            SELECT %1$L, '3_payments_wallet_student_mismatch', count(*)
              FROM %1$I.finance_payment p
              JOIN %1$I.finance_wallet w ON w.id = p.wallet_id
             WHERE p.student_id IS NOT NULL AND p.student_id <> w.student_id
            UNION ALL
            SELECT %1$L, '3_wallets_without_student', count(*)
              FROM %1$I.finance_wallet w
             WHERE NOT EXISTS (SELECT 1 FROM %1$I.students_student st WHERE st.id = w.student_id)
            UNION ALL
            SELECT %1$L, '3_coinwallets_without_student', count(*)
              FROM %1$I.coins_wallet cw
             WHERE NOT EXISTS (SELECT 1 FROM %1$I.students_student st WHERE st.id = cw.student_id)
            -- 4. СКОЛЬКО ИСТОРИИ УЖЕ ПОТЕРЯНО (ретроспектива по аудит-логу)
            UNION ALL
            SELECT %1$L, '4_audit_delete_student_attempts', count(*)
              FROM %1$I.audit_log WHERE action = 'delete' AND entity_type = 'students'
            UNION ALL
            SELECT %1$L, '4_audit_delete_student_gone', count(*)
              FROM %1$I.audit_log a
             WHERE a.action = 'delete' AND a.entity_type = 'students'
               AND a.entity_id ~ '^[0-9a-fA-F-]{36}$'
               AND NOT EXISTS (SELECT 1 FROM %1$I.students_student st WHERE st.id = a.entity_id::uuid)
            -- 5. сработавший fallback текущего destroy()
            UNION ALL
            SELECT %1$L, '5_archived_students_with_payments', count(DISTINCT st.id)
              FROM %1$I.students_student st
              JOIN %1$I.finance_wallet w ON w.student_id = st.id
              JOIN %1$I.finance_payment p ON p.wallet_id = w.id
             WHERE st.status = 'archived'
        $q$, s);
    END LOOP;
END
$do$;

SELECT schema_name, metric, cnt FROM r21_check WHERE cnt > 0 ORDER BY 1, 2;
SELECT metric, sum(cnt) AS total FROM r21_check GROUP BY metric ORDER BY 1;

ROLLBACK;
```

**Как читать результат:**

| Метрика | Ожидание | Что делать при отклонении |
|---|---|---|
| `1_students_blocked_by_payment`, `1_students_blocked_by_cointx` | любое | Это масштаб ожидаемого `ProtectedError`. Сообщить директорам центров, что удаление станет архивированием |
| `2_students_still_deletable` | > 0 | Подтверждает необходимость T-012. Само по себе миграцию не блокирует |
