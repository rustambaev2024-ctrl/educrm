# Стандарты Backend (Django 4.x / DRF)

Контекст обязателен: [[stack]] · [[multitenancy]] · [[api-map]] · [[data-model]]

## Мультитенант — красная зона
- Любой ORM-запрос только внутри контекста схемы тенанта
- **Celery-задача обязана явно устанавливать схему.** Воркер не наследует контекст запроса
- Redis-ключи включают идентификатор тенанта
- Channels group-имена включают идентификатор тенанта
- Пути MinIO включают идентификатор тенанта

## API
- Всё под `/api/v1/`, JWT Bearer обязателен (кроме `/auth/token/` и публичных)
- Ошибки: `{"detail": {"uz": "...", "ru": "..."}}` — **обе локали всегда**
- Валидация — в сериализаторах. Вьюха оркестрирует, не валидирует
- Права — через permission-классы, привязанные к 7 ролям из [[roles-permissions]]. Никаких `if user.role ==` внутри вьюхи
- Списки — с пагинацией и фильтрами. Без пагинации = деградация при масштабировании
- Не ломать контракт. Новое поле опционально; удаление — через ADR

## Деньги (`/payments/*`) — красная зона
- Изменение баланса только **в транзакции**, `select_for_update` на кошельке
- `balance_before` и `balance_after` пишутся всегда
- Операции **идемпотентны**: повторный вызов не списывает второй раз
- Списание за урок опирается на `is_charged`

## Celery
- Задача **идемпотентна** — beat может запустить повторно
- Явная установка схемы тенанта
- Таймаут и retry-политика заданы
- Логирование начала/конца с идентификатором тенанта
- Критичные задачи: `daily_lesson_charge`, перевод ДЗ в `overdue`, начисление монет

## Геймификация
Значения монет/XP/уровней — **только из `CoinSetting`**. Хардкод чисел в коде = баг.

## Тесты
Минимум на каждый эндпоинт: happy path · права для каждой роли · изоляция тенантов.

## Запрещено
- Секреты в коде и в git
- `print()` вместо логгера
- Бизнес-логика в миграциях
- Сырой SQL без обоснования и без учёта схемы тенанта
