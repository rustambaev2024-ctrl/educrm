# Окружения

Хостинг: **Railway**, проект `pleasing-trust`, автодеплой из GitHub.
Репозиторий: `https://github.com/rustambaev2024-ctrl/educrm`

| Окружение | Ветка | Назначение |
|---|---|---|
| **production** | `master` | Реальные данные реальных учебных центров |
| **staging** | `staging` | Проверка фич перед прод |
| рабочая | `fix` | Локальная ветка для правок |

> ⚠️ Старый `CLAUDE.md` утверждал, что деплой идёт из ветки `main`. **Ветки `main` в репозитории нет.** Перед любым hotfix-коммитом подтверждай, какая ветка реально задеплоена в Railway — через Railway MCP или дашборд, а не по памяти.

## Сервисы Railway
| Сервис | Что внутри |
|---|---|
| `educrm` | Backend: Daphne (ASGI) + Celery worker + beat, поднимаются `docker/start.sh` **внутри одного контейнера** |
| frontend | Vite build, статика |
| Postgres | База с volume |
| Redis | Кэш + брокер Celery + Channels layer, всё в db/0 |

## Опасная зона: конфиги Celery
В репозитории есть `railway.worker.toml` и `railway.beat.toml` с теми же командами, что уже запускает `docker/start.sh` (строки 35–41). Отдельных сервисов worker/beat в Railway **сейчас нет** — но конфиги вводят в заблуждение.

**Риск при следующем деплое: двойной запуск periodic-задач** (`daily_lesson_charge`, SMS-рассылки) = двойные списания с кошельков учеников.
Целевая архитектура пока не выбрана. См. [[risks]] и ADR — решение нужно принять до масштабирования.

## Правила
1. **Прямой пуш в `master` запрещён.** Только merge из `staging` после pass от QA и Наzorat
2. Любая фича сначала живёт на `staging`
3. Миграции: staging → проверка → prod. Всегда
4. `python manage.py migrate` **запрещён агентам** настройками — миграции на прод применяет человек
5. Секреты — только в переменных окружения Railway
6. Daphne + Celery worker + beat в одном контейнере: деплой перезапускает всё, рвёт WebSocket (live-квизы, мессенджер) и прерывает задачи. **Окно деплоя — не в часы занятий**
