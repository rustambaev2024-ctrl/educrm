# UX-аудит v2 — Design

Дата: 2026-08-25
Ветка: `design/ux-audit-v2`
Статус: approved (все пункты подтверждены пользователем в диалоге)

## Контекст и повод

Первый заход на UX (план `2026-08-15-ux-rebuild-design.md`, ветка `design/ux-rebuild-foundation`) закрыт полностью и живёт на проде — все 5 этапов, все 7 ролей, компонентная система (`PageShell`, `ConfirmDialog`, композитные скелетоны, `EmptyState`/`ErrorState`) введена и работает единообразно во всей кодовой базе.

Владелец продукта показал платформу нескольким учебным центрам. Обратная связь:
- **Клиенты в целом не заметили визуальных изменений** — ни в одной роли, включая учительскую.
- **Единственное, что реально зашло владельцу** — портал учителя, конкретно `Davomat` (посещаемость): общее ощущение «собрано для телефона». Остальные роли (админ, директор, суперадминистратор, ученик/родитель) на мобильном заметно слабее.
- **Изумрудная палитра v1** (`#0e7a57`) владельцу не понравилась лично, несмотря на задокументированное в коде обоснование контраста.

Это НЕ ребрендинг (не путать с незакоммиченной и неактуальной `2026-07-20-growbase-rebrand-foundation-design.md` — тот файл относится к отдельной, отложенной задаче ребрендинга EduCRM→GrowBase и не является частью этого аудита). Это второй полный проход по UX/UI с тем же по духу циклом, что и v1: аудит → IA/навигация → компоненты/архетипы → миграция по ролям → визуальный QA.

## Скоуп

**Полный аудит с нуля**, как в v1 — не точечная правка поверх существующей IA. Три направления ведутся в одном цикле:

1. **Палитра v2** — новый `--primary`, замена изумруда
2. **Glassmorphism** — стеклянность на карточках/панелях/оверлеях повсюду
3. **Мобильный аудит по образцу Davomat** — довести все роли до того же ощущения «собрано для телефона», что уже есть в посещаемости учителя

Бизнес-логика и API не меняются, если не потребуется явно (тот же принцип, что и в v1).

## 1. Палитра v2

### Основной цвет — Spicy Paprika

Владелец прогнал Coolors самостоятельно и указал конкретную палитру, которая зацепила сильнее остальных показанных вариантов (синий/индиго исключён explicit — «не хочу как у конкурентов», даже несмотря на то что это стандарт B2B/CRM). Инструкция: **использовать только цвета из уже показанных палитр, новых не добавлять.**

Выбранная палитра-источник (Coolors, скриншот владельца): `353531` (Charcoal Brown) / `EC4E20` (Spicy Paprika) / `FF9505` (Deep Saffron) / `016FB9` (Bright Marine) / `000000`, и вторая близкая палитра `E4572E` (Spicy Paprika) / `17BEBB` (Tropical Teal) / `FFC914` (Bright Amber) / `2E282A` (Shadow Grey) / `76B041` (Bright Fern) — из них редизайн берёт красно-оранжевый как primary.

- `--primary: #E4572E` (Spicy Paprika) — тёплый красно-оранжевый, контраст с белым текстом проверить (см. ниже), при необходимости взять затемнённый вариант `#c94a24` по той же логике, что и в v1 (светлый оттенок при белом тексте может недобирать AA).
- `--primary-foreground: #ffffff`
- `--ring`, `--accent`, `--accent-foreground` — производные от primary, тем же способом что в v1 (`--accent` = мягкий тон primary, `--accent-foreground` = затемнённый primary).

### Конфликт с --warn — решение

Оранжевый уже занят под `--warn` (предупреждение/долг) в v1. Если primary тоже оранжевый — кнопки и предупреждения визуально сольются. Решение: развести по тону внутри той же палитры без добавления новых цветов.

- `--primary`: `#E4572E` — **красно-оранжевый** (paprika)
- `--warn`: `#FFC914` / `#FF9505` — **жёлто-амбер** (amber/saffron)

Разница по оттенку (hue) достаточная — один читается как красноватый, другой как жёлтый, даже при беглом взгляде и при слабом цветовосприятии не пересекаются. Это тот же структурный подход, что развёл `--ok`/`--primary` в v1 (см. комментарий в `styles.css:158-162`) — задокументировать аналогичным комментарием.

### Sidebar / тёмные поверхности

Взять `Shadow Grey #2E282A` или `Charcoal Brown #353531` (из тех же палитр) под `--sidebar` вместо текущего тёмно-зелёного `#0a3527`, чтобы боковое меню не конфликтовало по смыслу с новым primary. `--sidebar-primary`/`--sidebar-ring` — оттенок paprika (по аналогии с v1, где `--sidebar-primary` был высветленным оттенком primary).

### Семантические цвета — не трогать

`--ok` (успех), `--bad` (опасность/удаление), `--info` — остаются как в v1. Логика "один цвет — один смысл" (столп 7) не меняется, меняется только сам primary и его сосед warn.

### Применение

Токенизация в `src/styles.css` уже единый источник (подтверждено: `--brand`, `--sidebar-bg` и т.д. — алиасы на базовые переменные, не отдельные хардкоды). Смена палитры — правка блока `:root` (и `.dark`, который зеркалит с более тёмными тонами) в одном файле, не поиск по кодовой базе. Раскатка по компонентам не требуется отдельным шагом, в отличие от v1, где токенизация создавалась впервые.

## 2. Glassmorphism

Владелец: «больше стеклянности в блоках», применить **повсюду**, не точечно — общий стиль продукта, а не единичные акцентные места.

### Что получает эффект
- `Card` (базовый компонент, `src/components/ui/card.tsx`) — полупрозрачный фон + `backdrop-blur`
- `Sheet` / `Dialog` / `Popover` / `DropdownMenu` содержимое — та же обработка на оверлейных поверхностях
- Боковое меню (`sidebar`) — сохраняет непрозрачность (навигационный якорь, стекло там мешало бы читаемости на цветном/сложном фоне), но получает лёгкий верхний градиент-блик для согласованности стиля

### Технический подход
- `background: color-mix(in srgb, var(--card) 72%, transparent)` (или fallback `rgba` для более широкой поддержки) + `backdrop-filter: blur(12px)`
- Тонкая граница `border: 1px solid color-mix(in srgb, var(--border) 60%, transparent)` вместо плотной — усиливает эффект "стекла"
- Мягкая тень (`shadow-elegant`/`shadow-glow` — уже существующие классы из v1) остаётся, возможно чуть смягчается
- **Обязательно** уважать `prefers-reduced-motion`/производительность: `backdrop-filter` дорогой на слабых мобильных устройствах при большом числе одновременно видимых карточек (списки/таблицы с carte-версией на мобильном, введённые в v1) — на страницах со списками из 20+ карточек рассмотреть отключение blur ниже некоторого количества видимых элементов или использование более лёгкого приближения (полупрозрачность без blur). Финальное решение — по факту профилирования на реальном устройстве в ходе миграции, не блокирует дизайн.
- Тёмная тема (`.dark`) получает свой набор полупрозрачных значений — та же осторожность, что и с остальными токенами v1 (не механическое затемнение, отдельная проверка контраста).

## 3. Мобильный аудит по образцу Davomat

### Что именно в Davomat работает (по формулировке владельца — «общее ощущение собрано для телефона»)
Проверить и явно выписать в план реализации конкретные технические приёмы `teacher/attendance.tsx` (уже зафиксированы в CLAUDE.md по итогам v1):
- `LessonPicker` — лента дат вместо длинного плоского списка
- `AttendanceBoard` — построен под тач, крупные зоны нажатия
- `StickyActionBar` — основное действие всегда на виду внизу экрана, не требует скролла до конца
- 44px+ тач-таргеты по всей странице

### Подход к остальным ролям
Не копировать компоненты `Davomat` дословно (разные роли — разные данные и действия), а **вынести общий паттерн** и применять по месту:
- Списки/ленты вместо таблиц-на-телефоне там, где сейчас используется только карточная проекция таблицы (`edu-cards`, введено в v1) — оценить по каждой роли, не является ли карточная проекция уже достаточной, или там, где данных много (расписание, начисления, заявки), нужна более специализированная лента как в Davomat
- `StickyActionBar`-паттерн — расширить на все экраны с одним основным действием (сохранить/отправить/подтвердить), где сейчас кнопка внизу обычной прокручиваемой формы
- Ревизия тач-целей per-role — `.edu-tap` класс из v1 уже покрывает `icon`-кнопки размером, но полный проход должен проверить остальные интерактивные элементы (переключатели, теги-фильтры, строки списков) на каждой странице

### Объём проверки
Все 78 страниц / 7 ролей — тот же формат, что в v1: инвентаризация функций по порталу → правка → ревью (spec-compliance + code-quality) → следующий портал. Порядок ролей не задан явно владельцем («все равно важны») — предлагается сохранить порядок v1 (учитель/помощник → ученик/родитель → администратор → суперадминистратор → директор), так как это уже проверенная последовательность от простого к сложному по объёму страниц.

## Явно вне скоупа

- **Ребрендинг** (переименование, лого, GrowBase) — отдельная, отложенная задача, не активируется этим планом.
- **IA/фича-логика Network/HQ для сети учебных центров** (см. память `educrm-network-multi-institution-lead`) — отдельный трек, ждёт деталей от клиента, не пересекается с этим аудитом.
- **Изменение бизнес-логики/API** — только если технически неизбежно (как в v1, где почти не потребовалось).

## Проверки перед закрытием (по аналогии с v1)
- `npm run build` чистый
- `tsc --noEmit` не хуже текущего базового уровня (21)
- Playwright — полный прогон + визуальная проверка на 375px (узкий мобильный) на ключевых страницах каждой роли, так как именно мобильный опыт — центральная претензия этого захода
- Контраст текста на новом `--primary`/`--warn` — проверить WCAG AA расчётом (как это было явно задокументировано в v1 для изумруда), не полагаться на глаз
