# Пересборка UX/UI EduCRM — проектное решение

Дата: 2026-08-15
Статус: на утверждение

## 1. Задача

Интерфейс строился на скорую руку, пока платформа росла. Сейчас в нём 78 страниц
и 7 ролей, и он не выдерживает собственного размера. Требуется пересобрать UX
по стандартам, а не косметически перекрасить.

## 2. Что показала разведка

### 2.1 Мобильной версии нет у 5 ролей из 7

| Роль | Страниц | Правил адаптива | Каркас |
|---|---|---|---|
| Ученик | 8 | 4 | `MobileLayout` |
| Родитель | 5 | 6 | `MobileLayout` |
| Учитель | 12 | 40 | `EnterpriseLayout` (десктоп) |
| Админ | 17 | 72 | `EnterpriseLayout` (десктоп) |
| Директор | 18 | 82 | `EnterpriseLayout` (десктоп) |
| Помощник учителя | 7 | 30 | `EnterpriseLayout` (десктоп) |
| Суперадмин | 5 | 13 | `EnterpriseLayout` (десктоп) |

Владелец подтвердил: **с телефона активно работают все семь ролей.** Учитель
ставит посещаемость стоя в классе и получает интерфейс под мышь и монитор.

`sidebar-layout.tsx` не используется ни одной страницей — мёртвый код.

### 2.2 Цвет живёт в трёх конкурирующих системах

1. Свои переменные: `--page-bg`, `--card-bg`, `--text-primary`, `--brand`
2. Токены shadcn: `--background`, `--primary`, `--card`
3. Прямые значения в разметке: **343 цветовых класса Tailwind + 159 hex-кодов в 26 файлах**

Нет одного места, где меняется цвет. Это корневая причина того, что дизайн
«ложился как было».

### 2.3 Тёмная тема — мёртвый код

Блок `.dark` существует, но копирует светлые значения («force light theme
always»). Переключатель есть, эффекта нет.

### 2.4 Документация противоречит сама себе

`DESIGN_SYSTEM.md` предписывает «Подтверждение удаления: ВСЕГДА `window.confirm`
или `AlertDialog`». `CLAUDE.md` предписывает «НИКОГДА `window.confirm`».
Оба файла активны. Правила спорят.

### 2.5 Страницы разрослись

`director/leads.tsx` 1062 строки, `admin/leads.tsx` 1054, `admin/groups.tsx` 809,
`admin/finance.tsx` 765. Две страницы лидов — почти дубликаты друг друга.
Итого в `src/routes/` 17 950 строк.

## 3. Принятые решения

Зафиксированы владельцем, 16 вопросов:

| № | Решение |
|---|---|
| 1 | Палитра — свести оба эскиза в одну систему |
| 2 | Тёмную тему убрать полностью |
| 3 | Плотность разная по ролям |
| 4 | Структуру менять можно, план согласовывать заранее |
| 5 | С телефона работают все 7 ролей |
| 6 | Мобильная навигация — 4 вкладки + «Ещё» |
| 7 | Таблицы на телефоне — строка становится карточкой |
| 8 | Устройства — средний класс, Android и iPhone |
| 9 | Начинаем с фундамента вместе с ролью учителя |
| 10 | Выкатываем по ролям, по мере готовности |
| 11 | Большие страницы переписываем с нуля |
| 12 | Цвет единый для всех организаций |
| 13 | Страховка — опись функций + автотесты, затем полная свобода |
| 14 | Проверка — на тестовом сервере (staging) |
| 15 | Графики — только там, где они по делу |
| 16 | Узбекский и русский равнозначны |

## 4. Архитектура

Четыре слоя. Каждый следующий опирается на предыдущий.

### Слой 1 — Токены (один источник правды)

Удаляются: все свои переменные (`--page-bg`, `--card-bg`, `--text-primary`,
`--brand*`, `--sidebar-*`) и весь блок `.dark`.

Остаются: только семантические токены shadcn, перекрашенные в зелёную систему.

**Палитра.** Два эскиза сводятся по ролям цвета, а не смешиванием:

| Роль цвета | Значение | Где применяется |
|---|---|---|
| Оправа | `#14372B` тёмно-зелёный | боковое меню, нижняя панель |
| Холст | `#FAF7F0` кремовый | фон страниц |
| Поверхность | `#FFFFFF` | карточки, панели |
| Действие | `#0A7357` изумруд | кнопки, ссылки, активное |
| Индикация | `#0F9E7A` светлый изумруд | полосы прогресса, метки |
| Награда | `#C9A227` золото | **только** система монет и знак в меню |

Золото не становится общим акцентом. У него одна работа — монеты и достижения
(разделы `coins` у ученика, учителя, директора). Это снимает конфликт с жёлтым
цветом предупреждения.

**Семантика.** `success` / `warning` / `danger` / `info` определяются один раз,
с проверенным контрастом на кремовом и на белом. Закрывается известный техдолг:
сейчас эти четыре токена заданы только в светлых значениях.

**Контраст.** Каждая пара «текст на фоне» проверяется до WCAG AA (4.5:1 для
обычного текста, 3:1 для крупного и элементов управления). Изумруд действия
взят затемнённым (`#0A7357`, контраст с белым 5.97:1) именно поэтому — исходный
`#0F9E7A` даёт 3.49:1 и не проходит для белого текста на кнопке.

**Плотность.** Атрибут `data-density` на корне каркаса переключает шкалу
отступов и размеров:

- `comfortable` — учитель, помощник, ученик, родитель
- `compact` — админ, директор, суперадмин

Это один набор компонентов, а не два. Меняются только значения токенов отступов.

### Слой 2 — Каркас приложения

Один компонент `AppShell` заменяет три (`EnterpriseLayout`, `MobileLayout`,
мёртвый `SidebarLayout`).

- Широкий экран: боковое меню в цвете оправы
- Узкий экран: 4 нижние вкладки + «Ещё», лист со всеми разделами
- Модальные окна на телефоне выезжают снизу
- Тач-цели не меньше 44px
- Набор из 4 вкладок задаётся отдельно для каждой роли, под её реальные задачи

### Слой 3 — Блоки данных

`DataView` — один компонент вместо 11 рукописных таблиц. Принимает описание
колонок и вид карточки. На широком экране рисует таблицу, на узком — карточки.

Главное в карточке крупно (имя, сумма, статус), второстепенное — мелко или по
нажатию.

Дополняются существующие `EmptyState`, `ErrorState`, `StatCard`, `PageHeader`.

### Слой 4 — Роли

По одной, каждая через тестовый сервер, затем в прод.

## 5. Порядок работ

| Этап | Содержание | Проверка |
|---|---|---|
| 0 | Токены, `AppShell`, `DataView` | обкатка на учителе |
| 1 | Учитель (12) + помощник (7) — один сценарий | staging → прод |
| 2 | Ученик (8) + родитель (5) — витрина для клиентов | staging → прод |
| 3 | Админ (17) — наибольший объём | staging → прод |
| 4 | Директор (18) | staging → прод |
| 5 | Суперадмин (5) | staging → прод |

Этап 0 невидим сам по себе, поэтому сдаётся вместе с этапом 1.

## 6. Порядок переписывания страницы

Владелец разрешил полную свободу — вплоть до объединения страниц и добавления
улучшений — **после** описи функций. Порядок обязателен:

1. **Опись.** Выписываю всё, что старая страница умеет: действия, фильтры,
   права по ролям, редкие ветки, обработку ошибок.
2. **Сверка.** Владелец читает опись и добавляет забытое.
3. **Тесты.** Поведение по описи фиксируется автотестами на старой странице.
4. **Переписывание.** Свобода формы при сохранении описи.
5. **Проверка.** Тесты проходят, страница открыта на staging.

Без шагов 1–3 переписывание не начинается.

## 7. Предлагаемые изменения структуры

Требуют отдельного согласования до реализации:

- **Объединить лиды.** `admin/leads.tsx` (1054) и `director/leads.tsx` (1062) —
  почти дубликаты. Одна страница с правами по роли вместо двух файлов.
- Аналогичная проверка на дубли: `daily-report`, `coins`, `messages`,
  `notifications`, `analytics`, `students`, `finance` — присутствуют у нескольких
  ролей.

Список дублей с оценкой выгоды готовится в начале этапа 3.

## 8. Что остаётся неизменным

- Вся логика работы с сервером (`src/lib/api.ts`, `src/lib/data/`)
- Бэкенд целиком
- Двуязычность: каждая надпись на узбекском и русском
- Подтверждение опасных действий через `ConfirmDialog`, не `window.confirm`
- Логотип и название организации подставляются из настроек клиента

## 9. Сопутствующие правки

- `DESIGN_SYSTEM.md` переписывается под новую систему; противоречие про
  `window.confirm` устраняется в пользу `ConfirmDialog`
- `CLAUDE.md` — раздел «8 столпов UI» приводится в соответствие
- `sidebar-layout.tsx` удаляется как мёртвый код
- В `CLAUDE.md` указана ветка деплоя `main`, фактически `master` — исправляется

## 10. Риски

| Риск | Мера |
|---|---|
| Потеря редкой функции при переписывании | Опись + сверка владельцем + тесты до начала |
| Разнобой: часть ролей новая, часть старая | Выкатка по ролям осознанно принята; общий каркас снимает визуальный разрыв |
| Правки цвета разъезжаются снова | Один источник токенов; прямые цвета в разметке запрещаются и вычищаются |
| Регресс на живых деньгах | Финансовые экраны (админ, директор) идут этапами 3–4, после обкатки каркаса |
