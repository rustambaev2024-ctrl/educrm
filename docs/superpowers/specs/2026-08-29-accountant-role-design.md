# Accountant Role — Design

Дата: 2026-08-29
Ветка: `feature/accountant-role`
Статус: approved (объём и ключевые решения подтверждены пользователем в диалоге; часть решений по последним разделам принята автономно по явному поручению — `/goal`: «доверяю тебе полностью, закрой всё с первого захода» — и задокументирована здесь для последующего ревью)

## Контекст и повод

Клиент попросил «бухгалтерский портал». У владельца продукта уточнено: это новая роль с новым функционалом, не просто урезанный доступ к тому, что уже видит директор. Сейчас в реальных центрах клиента бухгалтер существует, ведёт учёт в Excel и получает данные, заходя под логином директора или админа филиала — то есть с доступом ко всему лишнему (группы, ученики, персонал).

Перед проектированием проведено исследование (см. таблицу ниже, источники — в истории диалога):
- **Особенности Узбекистана** (не железно — требует проверки у местного бухгалтера/soliq.uz перед тем, как на это опираться в проде): отчётность **помесячная** (до 15 числа следующего месяца), приём оплат (включая Payme/Click, не только наличные) может требовать фискализации, акт сверки — не обязателен по закону, но стандартная практика для споров по задолженности.
- **Общий паттерн** across AlfaCRM/1С/iiko/QuickBooks/Xero: скоуп роли — только деньги (не трогает учеников/группы/HR); глагол роли — категоризировать и сверять, не решать (цены остаются за директором); **закрытие периода** — фирменная возможность, которой нет у обычного админа; экспорт/сверка — не довесок, а основная часть работы; нет доступа к управлению пользователями.

## Скоуп v1 (подтверждено пользователем)

1. Новая роль `accountant`, видит финансы **по всему учреждению** (как `director`, без фильтра по филиалу), не видит группы/учеников/расписание/персонал/настройки.
2. **Гибкий план счетов** — категории расходов управляемы (не хардкод), создаёт/выключает директор или бухгалтер.
3. Бухгалтер полноценно работает с деньгами: вносит/редактирует расходы, сторнирует платежи, рассчитывает и выплачивает зарплаты учителей, принимает оплаты от учеников — те же операции, что сейчас доступны директору/админу в `finance.tsx`/`salaries.tsx`.
4. **Закрытие месяца** — бухгалтер закрывает период, после чего прошлые платежи/расходы в нём нельзя сторнировать **даже директору**.
5. **Акт сверки** с учеником/родителем — экспорт-документ (период, начисления, платежи, баланс, подпись) — входит в v1.

## Архитектурное решение — не изобретать роль заново

В проекте уже 7 ролей, каждая — это (а) значение в `User.ROLE_CHOICES` (бэкенд), (б) папка `src/routes/<role>/` (фронтенд), (в) запись в `ROLE_HOMES`/`ROLE_LABELS`/`ROLE_DESCRIPTIONS` (`src/lib/roles.ts`), (г) скоуп в `get_queryset()` каждого вьюсета по образцу уже существующей ветки `if user.role in ("superadmin", "director"): scoped = qs` (без фильтра — то же самое даёт `accountant`). Ничего нового изобретать не нужно — просто восьмая роль по тому же чертежу.

Где новое: план счетов (сейчас его нет — категория расходов это `CharField` на 50 символов без модели), закрытие периода (сейчас нет вообще никакого механизма блокировки прошлых записей), акт сверки (сейчас нет — есть только generic-заглушка PDF/Excel экспорта, которая печатает JSON, не настоящий документ).

## 1. План счетов

Новая модель `finance.ExpenseCategory`:
```python
class ExpenseCategory(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    name_uz = models.CharField(max_length=100)
    name_ru = models.CharField(max_length=100)
    active = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)
```
Двуязычные поля, а не привязка к `i18n.tsx` — это данные конкретного учреждения (директор может завести «Ремонт кондиционеров»), не UI-текст платформы. `active`, не удаление: старый `Payment.category` должен остаться читаемым, даже если категорию выключили — выключенная просто не предлагается при вводе новой записи.

`Payment.category` (сейчас `CharField(max_length=50, blank=True)`) получает `category_fk = models.ForeignKey(ExpenseCategory, null=True, blank=True, on_delete=models.PROTECT)` — `PROTECT`, не `CASCADE`/`SET_NULL`: категорию с историческими платежами нельзя удалить физически вообще (только `active=False`), так что `PROTECT` здесь работает как дополнительная защита, а не просто формальность.

**Миграция данных.** Существующие 6 значений (`tuition`/`salary`/`rent`/`utilities`/`marketing`/`other`) становятся начальными строками `ExpenseCategory` (руками — 6 строк, оба языка берутся из уже существующих ключей `finance.cat.*` в `src/lib/i18n.tsx`). Data-migration проходит по всем `Payment` с непустым `category` и проставляет `category_fk` по соответствию строки. Старое поле `category` (CharField) **не удаляется** в v1 — остаётся как есть для обратной совместимости с уже написанным кодом фронтенда (`p.category`), которое ещё не переведено на `category_fk`; новое поле — источник истины для новых записей, старое — снимок для старых. Явный технический долг, задокументирован, не блокирует v1.

Права: `director` и `accountant` могут создавать/выключать категории. Все роли, у которых есть доступ к списку платежей, категорию только читают.

## 2. Закрытие месяца

Новая модель `finance.PeriodClose`:
```python
class PeriodClose(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    month = models.DateField()  # всегда 1-е число месяца
    closed_by = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.PROTECT, related_name="closed_periods")
    closed_at = models.DateTimeField(auto_now_add=True)
    reopened_by = models.ForeignKey(settings.AUTH_USER_MODEL, null=True, blank=True, on_delete=models.SET_NULL, related_name="reopened_periods")
    reopened_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        constraints = [models.UniqueConstraint(fields=["month"], condition=Q(reopened_at__isnull=True), name="one_open_close_per_month")]
```
Институт-вайд (без филиала) — согласовано со скоупом роли: один бухгалтер закрывает месяц для всего учреждения разом, не по филиалам отдельно.

**У `Payment` сейчас нет отдельной даты операции** — только `created_at = auto_now_add`, то есть запись всегда датируется «сейчас». Это упрощает и одновременно ограничивает дизайн:
- Новую запись физически невозможно создать «в прошлом» без явного механизма бэкдейтинга, которого сейчас нет. Добавляю `transaction_date = models.DateField(null=True, blank=True)` на `Payment` — по умолчанию равен дате создания, но **бухгалтер** (не директор, не админ — это намеренное сужение: бэкдейтинг это бухгалтерская операция) может при вводе расхода указать более раннюю дату (например, счёт за аренду за прошлый месяц, полученный сегодня) — с проверкой, что указанная дата не попадает в уже закрытый период.
- Закрытие периода блокирует **сторно** записей, чей `transaction_date` (или `created_at.date()`, если `transaction_date` не задан — старые записи) попадает в закрытый месяц.

**Где именно проверка.** Не внутри `reverse_payment()` в `finance/services.py` — эта функция дёргается из трёх мест (кнопка в UI, сигнал «уважительная причина», команда `refund_phantom_charges`), и последние два — это внутренние механизмы целостности данных, а не интерактивная бухгалтерская работа; блокировать им доступ к историческим записям значило бы, что закрытие месяца тихо ломает возврат ошибочных списаний за прошлые периоды. Проверка — в `PaymentViewSet.reverse()` (view-слой, интерактивный путь), возвращает `409` с понятным сообщением, если период закрыт. Это сознательная граница, а не недосмотр — явно прокомментирована в коде.

**Кто может переоткрыть.** Только `accountant` (закрывший или любой другой бухгалтер — не обязательно тот же самый), не `director` — это то самое требование «даже директору нельзя», реализовано буквально: у директора нет ни кнопки закрытия, ни кнопки переоткрытия, только просмотр статуса периода.

Права на закрытие/переоткрытие: только `accountant`. `director`/`branch_admin` видят статус («Август закрыт бухгалтером Х числа»), не управляют им.

## 3. Акт сверки

Существующий `backend/apps/reports/exporters.py` — общий `export_pdf(report_type, data)`, который рендерит JSON внутри `<pre>` через WeasyPrint (либо самодельный минимальный PDF-фоллбэк, если WeasyPrint недоступен) — годится для внутренних технических отчётов, но не для документа, который выдают родителю на подпись. Акт сверки получает **свой** HTML-шаблон (`backend/apps/reports/templates/reconciliation_act.html` — заголовок учреждения, ФИО ученика, период, таблица начислений/платежей с бегущим балансом, итоговая строка, место под подпись и дату) и отдельную функцию `export_reconciliation_pdf(data)` в том же модуле, использующую тот же паттерн `try WeasyPrint / except → fallback`, что и существующий код — не новая инфраструктура, новый шаблон поверх существующей.

Endpoint: `GET /api/v1/reports/reconciliation/<student_id>/?date_from=&date_to=&format=pdf|excel` — доступен `accountant` и `director` (не только бухгалтеру — директору тоже может понадобиться этот документ). Данные: `Payment.objects.filter(student=student, created_at__range=...)`, начальный баланс (сумма всех операций до `date_from`), список операций по порядку с бегущим балансом, итоговый баланс. Excel-экспорт переиспользует существующий `export_excel()` — табличные данные туда ложатся без переделок.

## 4. Роль и права — сводка

| Что | Кто может (кроме superadmin) |
|---|---|
| Смотреть/принимать платежи, вносить расходы | `director`, `branch_admin` (как сейчас), `accountant` (ново) |
| Сторнировать платёж | `director`, `branch_admin`, `accountant` — если период открыт |
| Управлять планом счетов | `director`, `accountant` |
| Закрыть/переоткрыть период | только `accountant` |
| Рассчитать/выплатить зарплату | `director`, `accountant` |
| Сгенерировать акт сверки | `director`, `accountant` |
| Группы/ученики/расписание/персонал/настройки | **не** `accountant` — явный вырез, роль не видит эти разделы вообще (не urlа, не в меню) |

## 5. Фронтенд — структура

`src/routes/accountant/` (новая роль → новая папка, по образцу существующих):
- `index.tsx` — дашборд: доход/расход за месяц, статус периода (открыт/закрыт), число должников, быстрые действия
- `finance.tsx` — платежи + сторно. Переиспользует уже провалидированный код `director/finance.tsx` (защищённые денежные функции `handleReverse`/`confirmReverse`, деривации баланса) через общий компонент/переиспользуемую логику, а не копипаст — если директорская версия чинится, бухгалтерская не должна расходиться отдельным багом
- `expenses.tsx` — ввод/редактирование расходов с выбором категории (план счетов), кнопка «Закрыть месяц» / «Переоткрыть» с диалогом подтверждения (`ConfirmDialog`, не `window.confirm`)
- `salaries.tsx` — переиспользует `director/salaries.tsx`
- `reconciliation.tsx` — выбор ученика + периода, предпросмотр, экспорт PDF/Excel

`ROLE_HOMES.accountant = "/accountant"`, `ROLE_LABELS.accountant = "Buxgalter"`, добавить в `Role` union-тип в `src/lib/roles.ts`.

## Явно вне скоупа v1

- Фискализация/онлайн-касса (Узбекистан-специфика не подтверждена окончательно — если потребуется, это отдельная интеграция с провайдером фискальных чеков, не часть этой роли)
- Разбивка плана счетов и закрытия периода по филиалам отдельно (сейчас — институт-вайд)
- Экспорт в формат обмена с 1С
- Многоуровневые права внутри роли accountant (главный бухгалтер vs рядовой) — пока одна роль, без иерархии

## Проверки перед закрытием

- `npm run build`, `tsc --noEmit` не хуже базового уровня (21)
- `python manage.py check`, миграции применяются на чистой БД без ошибок
- Data-migration категорий проверяется на количестве совпавших/несовпавших строк (лог, не молчаливый пропуск)
- Playwright: новый профиль `accountant` в nav-model, закрытие периода блокирует сторно даже под директором — отдельный тест именно на этот сценарий, поскольку это самое неочевидное поведение всего фича-сета
