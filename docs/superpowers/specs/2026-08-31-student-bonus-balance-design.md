# Бонусный баланс ученика — дизайн-спека

**Дата:** 2026-08-31
**Статус:** утверждено владельцем в диалоге, ждёт финального ревью спеки
**Ветка реализации:** `feature/student-bonus-balance` (создать от `master`)

## Зачем

Директор/администратор филиала хочет вручную начислить ученику бонусные
деньги (например, за приведённого друга, в качестве компенсации, как
поощрение) — отдельно от обычного пополнения баланса. Когда у ученика не
хватает денег на основном балансе для списания за очередной урок (или
основной баланс уже исчерпан), недостающая часть списывается из бонуса,
а не сразу уходит в минус.

## Что уже согласовано с владельцем (не пересматривать без явного запроса)

1. **Должник считается по сумме основного баланса и бонуса вместе.**
   Ученик с основным балансом 0 и бонусом 5000 — не должник, пока бонус
   это покрывает.
2. **Списание за урок при нехватке основного баланса — разбивается**
   между основным балансом и бонусом (не «всё или ничего»). Пример: цена
   урока 5000, на основном осталось 3000 → 3000 списывается с основного,
   2000 — с бонуса, обе операции попадают в журнал платежей отдельными
   записями.
3. **У бонуса нет срока действия в v1.** Висит на ученике бессрочно, пока
   не потрачен на уроки или не отменён вручную.
4. **Отмена ошибочного начисления — как сторно у обычных платежей.** Если
   часть бонуса уже потрачена на уроки, отмена возвращает только то, что
   реально осталось на бонусном счету — не всю исходную сумму.
5. **Ученик и родитель видят бонус отдельной строкой** в своём личном
   кабинете: «Основной баланс X + Бонус Y», а не одно слитое число.
6. **Директору/админу на сводных экранах** (KPI-плитки, список
   должников, дневной отчёт) — **ничего визуально не меняется**, то же
   одно число баланса, что и сейчас, просто это число уже честно
   учитывает бонус при решении «должник или нет». Разбивка на «основной +
   бонус» видна только там, где реально работают с деньгами конкретного
   ученика.
7. **Начислять бонус может** director, branch_admin, superadmin (тот же
   набор ролей, что уже имеет право работать с деньгами в Финансах — см.
   `IsBranchAdmin` в `backend/apps/accounts/permissions.py`).
8. **Вне объёма v1 (сознательно не делаем сейчас):** срок действия/сгорание
   бонуса, ручное списание бонуса на что-либо кроме уроков, массовое
   начисление бонуса нескольким ученикам разом.

## Текущее устройство денег (контекст, для понимания блast radius)

Прочитано и проверено по коду перед дизайном (не переписывать заново —
ссылки ниже точные):

- `Wallet` (`backend/apps/finance/models.py`) — один баланс на ученика.
  `Student.wallet_balance` — денормализованное зеркало того же числа,
  оба поля обновляются в одной транзакции внутри `apply_payment()`
  (`backend/apps/finance/services.py`). Если разойдутся —
  `get_or_create_wallet()` логирует и чинит по `Student.wallet_balance`
  как источнику правды; есть отдельная management-команда
  `sync_balances.py` для ручной починки на реальных данных.
- `Payment` — неизменяемый журнал (append-only), у каждой записи
  `balance_before`/`balance_after`. Ничего не редактируется задним
  числом, только новые записи + запись-сторно с комментарием
  `f"Reversal of payment {id}"`, по которому `reverse_payment()`
  определяет, что платёж уже отменён (защита от двойной отмены).
- **Списание за урок сегодня НЕ проверяет баланс вообще** —
  `charge_groups_for_day()` (`backend/apps/finance/tasks.py`) всегда
  списывает цену урока с каждого присутствовавшего/опоздавшего ученика,
  баланс просто уходит в минус, статус меняется на `debtor`. Отдельной
  ветки «не хватает денег» в коде нет нигде — это первое место, где она
  появится.
- Цена одного урока: `calculate_lesson_price()` —
  `group.monthly_price / (число дней недели по расписанию группы,
  попадающих на текущий календарный месяц)`.
- `payment_type="charge"` **создаётся только в одном месте** —
  `charge_groups_for_day()`. Прямого пути «администратор вручную
  списывает `charge`» в UI нет (проверено — в `admin/finance.tsx` такой
  кнопки нет). Значит логика разбивки основной/бонус нужна ровно в одном
  месте бэкенда, не размазана по всему приложению.
- `is_debtor_balance(balance)` (`backend/apps/core/definitions.py`) —
  единственное место, откуда решение «должник» расходится по системе
  (KPI-плитки, SMS-напоминания должникам, дневной отчёт, цвет статуса).
  **У этой функции нет фронтенд-зеркала** — фронт нигде не пересчитывает
  «должник» сам, везде читает уже готовое поле `student.status` с
  бэкенда. Значит менять нужно только бэкенд-функцию, тест
  `test_definitions_parity.py` её не проверяет (сверяет только константы-
  наборы, не эту функцию — см. список `PARITY_CONSTANTS` в файле теста).
- `reverse_payment()` — по `payment.payment_type` создаёт зеркальную
  операцию (`charge`→`refund`, `top_up`→`manual_charge`,
  `manual_charge`→`manual_top_up`, и т.д.), с блокировкой строки
  (`select_for_update`) и явной проверкой повтора внутри самой функции
  (не только во вьюхе — отмену запускают три независимых источника:
  кнопка в интерфейсе, сигнал «уважительная причина», команда возврата
  ошибочных списаний).
- `refund_lesson_charges(lesson, ...)` — общий возврат для трёх поводов
  (урок отменили/перенесли/уважительная причина): фильтрует
  `Payment.objects.filter(lesson=lesson, payment_type="charge")` и
  вызывает `reverse_payment()` для каждой найденной записи. **Уже
  устроен так, что если списание за урок породит две записи (основной +
  бонус), обе будут найдены и возвращены этим циклом без единой правки
  в нём** — только `reverse_payment()` должен знать, в какой счёт
  возвращать деньги.

## Бэкенд: сервисный слой (`backend/apps/finance/services.py`)

### `apply_payment()` — новый параметр

```python
def apply_payment(
    student, payment_type, amount, *,
    created_by=None, group=None, lesson=None, method="", category="tuition",
    comment="", suppress_notifications=False,
    funding_source: str = "main",   # НОВОЕ
) -> PaymentResult:
```

Логика внутри меняется точечно:
- `delta = wallet_delta(payment_type, amount)` — без изменений (знак по
  типу операции, как сейчас).
- Если `funding_source == "bonus"`: `balance_before`/`balance_after`
  читаются и пишутся в `wallet.bonus_balance` /
  `student.bonus_balance`, а не в `wallet.balance` /
  `student.wallet_balance`.
- `Payment.objects.create(..., funding_source=funding_source)`.
- **`_status_changed_for_balance()` и уведомление «баланс стал
  отрицательным» вызываются только когда затронут ОСНОВНОЙ баланс**
  (`funding_source == "main"`) — начисление или списание бонуса само по
  себе не меняет статус ученика напрямую (см. ниже отдельную функцию для
  пересчёта статуса по сумме).

### Новая функция: пересчёт статуса по объединённому балансу

```python
def _status_changed_for_combined_balance(student: Student) -> bool:
    """Единая точка, откуда меняется student.status по правилу
    is_debtor_balance(main + bonus). Вызывается после ЛЮБОЙ операции,
    затронувшей main или bonus — начисление/списание бонуса тоже может
    вывести ученика из статуса "должник" или наоборот."""
```
Использует уже существующий `is_debtor_balance()` из
`apps/core/definitions.py`, но с суммой `wallet.balance + wallet.bonus_balance`
вместо одного `balance`. Вызывается из `apply_payment()` после любой
операции, вне зависимости от того, какой счёт она затронула — потому что
даже чистое начисление бонуса без единого списания урока может «вывести
ученика из долга» с точки зрения `is_debtor_balance`.

`_status_changed_for_balance()` (старая функция) удаляется, её вызовы в
`apply_payment()` заменяются на новую. Ссылка на старое имя функции в
докстринге `is_debtor_balance()` (`apps/core/definitions.py`) —
поправить на новое имя, чтобы комментарий не указывал на несуществующий
код.

### Второе место, которое считает "должник" независимо — обязательно поправить

**Найдено при само-ревью спеки, не было очевидно из первого чтения
`services.py`.** Ночная Celery-задача `update_debtor_statuses()`
(`backend/apps/finance/tasks.py`) — это отдельный, независимый механизм
починки рассинхрона статуса и баланса (был специально заведён раньше,
чтобы статус не отставал от баланса). Она **не использует
`is_debtor_balance()` вообще** — сравнивает `wallet_balance` с нулём
напрямую двумя `.filter(...).update(...)` запросами:

```python
cleared = Student.objects.filter(status="debtor", wallet_balance__gte=0).update(status="active")
marked = Student.objects.filter(status="active", wallet_balance__lt=0).update(status="debtor")
```

Если оставить как есть, эта задача **каждую ночь будет откатывать**
статус ученика, которого новая логика корректно держит "не должником"
благодаря бонусу (`wallet_balance=-1000`, `bonus_balance=2000`) — задача
увидит только `wallet_balance < 0` и пометит его должником, входя в
прямое противоречие с `apply_payment()`. Это ровно тот класс бага (одно
и то же правило посчитано по-разному в двух местах), ради которого
существует `apps/core/definitions.py`.

**Обязательная правка:** оба запроса переписать через аннотацию суммы
`main + bonus`:
```python
from django.db.models import F
combined = F("wallet_balance") + F("bonus_balance")
cleared = Student.objects.filter(status="debtor").filter(combined__gte=0).update(status="active")
marked = Student.objects.filter(status="active").filter(combined__lt=0).update(status="debtor")
```
(точный синтаксис аннотации — на усмотрение реализации, суть: сравнение
должно идти по сумме двух полей, не по одному). Комментарий в докстринге
про «тем же правилом, что и `finance.services._status_changed_for_balance`»
тоже поправить на новое имя функции.

### Полный список мест, читающих `wallet_balance` напрямую как «должник» — обязательно поправить все

**Найдено сплошным `grep` по бэкенду при само-ревью спеки — их 9, не 2,
как казалось из первого чтения `services.py`/`tasks.py`.** Каждое из
них — независимая, отдельно написанная копия правила «баланс меньше
нуля = должник», в обход `is_debtor_balance()`. Если поправить не все —
получится ровно то, чего владелец просил избежать: на одном экране
ученик не должник (спасибо бонусу), на другом — до сих пор должник,
потому что тот конкретный экран считает по-старому.

Не чинить каждое место ad hoc отдельной правкой — завести один общий
переиспользуемый хелпер в `apps/core/definitions.py`:
```python
from django.db.models import F, QuerySet

def with_combined_balance(queryset: QuerySet) -> QuerySet:
    """Аннотирует queryset учеников полем combined_balance = wallet_balance +
    bonus_balance. Использовать вместо прямой фильтрации по wallet_balance
    везде, где решается вопрос "должник или нет" — единая точка того, что
    складывается, при следующем изменении (например, появится третий вид
    баланса) правится один раз, а не в 9 местах."""
    return queryset.annotate(combined_balance=F("wallet_balance") + F("bonus_balance"))
```
Каждый из 9 call-site заменяет `.filter(wallet_balance__lt=0)` на
`with_combined_balance(qs).filter(combined_balance__lt=0)`, а там, где
`wallet_balance` дальше используется как *отображаемая сумма долга*
(не только как условие фильтра) — сумма тоже берётся из
`combined_balance`, а не из сырого `wallet_balance`, иначе директор или
родитель увидит завышенную цифру долга, не учитывающую бонус:

1. `apps/finance/tasks.py:254,257` — `update_debtor_statuses()` (см.
   выше, уже описано подробно).
2. `apps/institutions/views.py:85` — `BranchViewSet.debtors` action
   (`GET /api/v1/branches/{id}/debtors/`) — список должников филиала;
   payload отдаёт `wallet_balance` как есть, заменить на
   `combined_balance`.
3. `apps/notifications/tasks.py:80` — `debtor_reminder()`, еженедельное
   уведомление директору «N должников, всего долга X» (см. выше).
4. `apps/notifications/tasks.py:239` — `send_debtor_sms()`, реальная SMS
   ученику/родителю с суммой долга (см. выше) — **самое чувствительное
   место**: если не поправить, семья получит SMS с требованием оплатить
   долг, который на самом деле уже покрыт бонусом.
5. `apps/reports/services.py:120` — `get_overview()`, KPI-плитка
   «Должники» в аналитике директора/админа.
6. `apps/reports/services.py:426` — `get_debtors_report()`, отчёт по
   должникам (вкладка «Должники» в Финансах, экспорт).
7. `apps/reports/services.py:635` — внутри `get_daily_report()`, поле
   `total_debt` в Дневном отчёте (заголовок секции «Финансы»).
8. `apps/reports/services.py:870` — внутри `get_group_report()`, список
   должников конкретной группы (`GroupReportSheet` в
   `admin/groups.tsx`/`director/courses.tsx`).

Тест на этот хелпер и на то, что все 9 мест дают согласованный результат
на одних и тех же тестовых данных (ученик с отрицательным основным и
покрывающим бонусом не должен попадать ни в один из 9 списков/счётчиков
как должник) — отдельный явный пункт в разделе «Тестирование» ниже, не
полагаться на то, что unit-тест одного места гарантирует остальные 8.

### `backend/apps/core/definitions.py::is_debtor_balance`

Сигнатура и тело не меняются (`balance < 0` остаётся верным правилом) —
меняется только ЧТО ей передают на вход (сумма, а не одно поле). Функция
остаётся простой и переиспользуемой, вся сложность «что складывать»
остаётся в вызывающем коде (`_status_changed_for_combined_balance`).

### Новая функция: разбивка списания за урок

```python
def charge_for_lesson(
    student: Student, group, lesson, lesson_price: Decimal,
    *, category: str, comment: str, created_by=None,
) -> list[PaymentResult]:
    """Списывает lesson_price за урок, разбивая между основным балансом
    и бонусом. Основной баланс покрывает столько, сколько на нём
    ПОЛОЖИТЕЛЬНОГО есть (уже отрицательный баланс не считается
    "доступным" — тогда всё сразу уходит в бонус). Остаток берётся из
    бонуса, не больше, чем там реально есть. Если и бонуса не хватило —
    непокрытый остаток списывается с основного, уходя в минус, как и
    раньше. Возвращает 1 или 2 PaymentResult (одна запись, если счёт
    всего один; две — если списание разбилось)."""
    wallet = get_or_create_wallet(student)
    main_available = max(wallet.balance, Decimal("0.00"))
    from_main = min(lesson_price, main_available)
    remainder = lesson_price - from_main
    from_bonus = min(remainder, wallet.bonus_balance) if remainder > 0 else Decimal("0.00")
    from_main_final = lesson_price - from_bonus

    results = []
    if from_bonus > 0:
        results.append(apply_payment(
            student=student, payment_type="charge", amount=from_bonus,
            group=group, lesson=lesson, category=category, comment=comment,
            created_by=created_by, funding_source="bonus",
        ))
    if from_main_final > 0:
        results.append(apply_payment(
            student=student, payment_type="charge", amount=from_main_final,
            group=group, lesson=lesson, category=category, comment=comment,
            created_by=created_by, funding_source="main",
        ))
    return results
```

**`backend/apps/finance/tasks.py::charge_groups_for_day()`** — единственный
вызывающий код, который сейчас напрямую зовёт `apply_payment(student=...,
payment_type="charge", amount=lesson_price, ...)`. Заменяется на вызов
`charge_for_lesson(...)`. Остальная логика функции (кого списывать,
идемпотентность по `already_charged_ids`, bulk-update `is_charged`) не
меняется — `charge_for_lesson` подставляется на место одного вызова
`apply_payment`, `charged_total` считается по факту хотя бы одного
успешного `PaymentResult` в списке.

### `reverse_payment()` — сохранение `funding_source`

Каждый вызов `apply_payment(...)` внутри `reverse_payment()` (для всех
веток: `charge`→`refund`, `top_up`→`manual_charge`,
`manual_charge`→`manual_top_up`, `manual_top_up`→`manual_charge`)
получает дополнительный аргумент `funding_source=payment.funding_source` —
то есть зеркальная операция всегда возвращает деньги туда же, откуда они
были списаны/начислены. Это единственная точечная правка в этой функции:
не переписывать структуру веток, только добавить проброс поля.

**Особый случай: отмена начисления бонуса, если часть уже потрачена.**
`payment.payment_type == "top_up"` с `funding_source == "bonus"` →
реверс создаёт `manual_charge` с `funding_source="bonus"`. Если
`amount` реверса больше, чем текущий `wallet.bonus_balance` (часть уже
ушла на уроки), `apply_payment()` **не должен позволить бонусу уйти в
минус** — сумма реверса обрезается до `min(payment.amount,
wallet.bonus_balance)` **до** вызова `apply_payment`, и в ответе/тосте
явно указывается, что возвращено меньше исходно начисленного (см. раздел
API/UI ниже — это принципиальное отличие от реверса `top_up` на основной
баланс, где такого ограничения сегодня нет и не вводится). Место правки:
в `reverse_payment()`, отдельная ветка перед вызовом `apply_payment` для
случая `payment_type == "top_up" and payment.funding_source == "bonus"`.

## Бэкенд: API

### Начисление бонуса

Переиспользуется существующий `POST /api/v1/payments/` (view —
`PaymentViewSet.create`, сериализатор — `PaymentCreateSerializer`,
`backend/apps/finance/serializers.py`) — **новый эндпоинт не создаётся**,
чтобы не плодить второй путь создания платежа рядом с уже
протестированным. `PaymentCreateSerializer` получает новое поле:

```python
funding_source = serializers.ChoiceField(
    choices=["main", "bonus"], required=False, default="main",
)
```

В `validate()` — если `funding_source == "bonus"`, разрешено только для
`payment_type == "top_up"` (начисление бонуса) и, отдельно,
`payment_type in ("charge", "manual_charge", "manual_top_up")` только со
стороны `reverse_payment` (не напрямую через этот эндпоинт — прямое
создание `charge`/`manual_charge` с `funding_source="bonus"` через этот
публичный API запрещается явной проверкой роли/типа, чтобы не открыть
случайный путь обойти правило «бонус тратится только на уроки»). Права
доступа не меняются — тот же `IsBranchAdmin`, что уже стоит на
`PaymentViewSet` для операции создания.

### Отмена

Существующий `POST /api/v1/payments/{id}/reverse/` без изменений
контракта — только внутреннее поведение `reverse_payment()` (см. выше).

### Чтение баланса

`PaymentSerializer`/`Wallet`-related сериализаторы, отдающие баланс
ученика фронту (используются в `admin/students`, `admin/finance`,
`director/finance`, мобильные `student`/`parent` эндпоинты) — добавить
поле `bonus_balance` рядом с уже существующим `balance`/`wallet_balance`
везде, где эти сериализаторы сейчас отдают основной баланс. Не
создавать отдельный эндпоинт «баланс бонуса» — это то же самое место в
ответе API, просто с одним новым полем.

## Фронтенд

### Типы (`src/lib/data/types.ts`)

`Student.balance` — без изменений по смыслу (продолжает быть
объединённым числом, как сейчас, ничего не переименовывать, чтобы не

### Начисление бонуса — UI

**Проверено по коду:** сегодня `director/finance.tsx` вообще не умеет
создавать платежи — ни принять оплату, ни добавить расход, только

## Тестирование

Новый файл `backend/tests/test_bonus_balance.py`:
- Начисление бонуса создаёт `top_up`/`bonus`, увеличивает
  `wallet.bonus_balance`, не трогает `wallet.balance`.
- Списание за урок при основном балансе, полностью покрывающем цену —
  бонус не тронут, одна запись `charge`/`main`.
- Списание за урок при основном балансе 3000 и цене урока 5000, бонусе
  ≥2000 — две записи (`charge`/`main` на 3000, `charge`/`bonus` на
  2000), обе с корректными `balance_before`/`balance_after` для своего
  счёта.
- Списание за урок при основном балансе уже отрицательном — 100%
  пытается уйти в бонус, при нехватке бонуса непокрытая часть уходит в
  минус на основной, как раньше.
- Должник: основной баланс 0, бонус 5000 → `status != "debtor"`.
  Основной баланс -1000, бонус 500 → `status == "debtor"` (сумма
  отрицательна).
- **Кросс-проверка всех 9 мест разом**, не по отдельности: один ученик
  с основным балансом -1000 и бонусом 2000 создаётся в тесте один раз,
  затем последовательно проверяется, что он НЕ входит в: список
  должников филиала (`BranchViewSet.debtors`), еженедельный
  `debtor_reminder`, `send_debtor_sms`, KPI `get_overview`,
  `get_debtors_report`, `total_debt` в `get_daily_report`, список
  должников в `get_group_report`, и что `update_debtor_statuses` не
  переводит его в `debtor`. Один тест на все 8 потребителей + сама
  функция статуса — чтобы будущая правка, задевшая только часть списка,
  падала здесь, а не находилась вручную через полгода.
- Отмена начисления бонуса, когда часть уже потрачена на урок — реверс
  ограничен остатком, `wallet.bonus_balance` не уходит в минус.
- `refund_lesson_charges` на уроке, где списание было разбито на
  main+bonus — возвращает обе записи, оба счёта восстанавливаются
  корректно.

Существующий `backend/tests/test_finance_services.py` — единственный
имеющийся сейчас файл денежных тестов (`test_period_close_blocks_reversal.py`
из откаченной ветки `feature/accountant-role` в кодовой базе больше нет,
проверено — `ls backend/tests/` не находит) — прогоняется как регресс
без изменений.
