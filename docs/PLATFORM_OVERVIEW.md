# EduCRM — обзор платформы для внешних агентов

> Составлено по факту кода на коммит `ab0b9da` (2026-08-30, ветка `master`).
> Каждый пункт ниже проверен чтением реального файла, а не по памяти —
> но код меняется быстрее документа, так что при спорном вопросе сверяйтесь
> с файлом напрямую (путь указан).

## Что это за продукт

CRM для учебных центров (репетиторские курсы, языковые школы и т.п.).
Мультитенантная SaaS: одна кодовая база, у каждого учебного центра —
своя изолированная схема БД (`django-tenants`, `TENANT_MODEL =
tenants.Institution`). Один Institution может иметь несколько физических
филиалов (`Branch`).

**Стек:**
- Frontend: React 19 + TypeScript + TanStack Router + TanStack Start,
  Tailwind v4, shadcn/ui (`new-york` preset, Radix primitives), Recharts
  для графиков, `cmdk` для поиска, `xlsx` для экспорта, Sentry для ошибок.
- Backend: Django + DRF, PostgreSQL, Celery (беат-задачи + воркер), Redis
  (кэш + брокер + WebSocket channels).
- Реальный размер: ~19К строк роутов, ~13К строк общих компонентов,
  ~18К строк бэкенд-кода на Python. 79 файлов-страниц.

## Роли

Семь ролей в `User.ROLE_CHOICES` (`backend/apps/accounts/models.py`) +
`superadmin`:

| role (в коде) | Кто это | Домашняя страница | Портал |
|---|---|---|---|
| `superadmin` | Оператор платформы, вне конкретного учебного центра | `/superadmin` | Управление тенантами |
| `director` | Владелец/руководитель учебного центра, видит всё учреждение целиком | `/director` | Самый крупный портал |
| `branch_admin` | Администратор конкретного филиала, операционка | `/admin` | Второй по размеру |
| `teacher` | Учитель | `/teacher` | |
| `support_teacher` | Помощник учителя (более узкие права, чем у учителя) | `/support-teacher` | |
| `student` | Ученик | `/student` | Мобайл-фёрст |
| `parent` | Родитель, привязывается к ученику по коду | `/parent` | Мобайл-фёрст, самый тонкий |

**Важная историческая деталь:** в коде есть ещё роль `"admin"` — это
**удалённая** миграцией `accounts/0004_merge_admin_into_branch_admin.py`
роль, слитая в `branch_admin`. Она до сих пор упоминается в 5 местах
фронтенда как техдолг (`messenger-panel.tsx`, `store.tsx` ×2,
`superadmin/logs.tsx` ×2) — **не путать её с реальной активной ролью**,
это мёртвый код, который никто не видит в реальности.

Папка `src/routes/admin/` в названии файлов — это портал `branch_admin`,
не мифического `admin`. Путаница только в имени папки.

### Проверка прав на бэкенде

`backend/apps/accounts/permissions.py` — набор классов-разрешений,
каждый следующий — надмножество предыдущего:

```
IsSuperAdmin       → только superadmin
IsDirector         → superadmin, director
IsBranchAdmin      → superadmin, director, branch_admin
IsTeacher          → superadmin, director, branch_admin, teacher
IsSupportTeacher   → только support_teacher
IsTeacherOrSupport → teacher, support_teacher
IsStudent          → только student
IsParent           → только parent
```

Скоуп данных (кто что видит) решается не только этим — почти в каждом
`get_queryset()` есть ветвление по `user.role` вручную (см. пример в
`students/views.py`, `finance/views.py`, `courses/views.py`,
`lessons/views.py`) — обычно по схеме: superadmin/director видят всё
учреждение → branch_admin/teacher видят свой филиал/свои группы →
support_teacher видит группы своего учителя (уже отфильтровано на
бэкенде, фронт доверяет этому) → student/parent видят только себя/своих
детей.

## Что реально делает каждая страница

### superadmin

**`/superadmin` — Организации** (`superadmin/index.tsx`, 628 строк).
Заведение и администрирование учебных центров (тенантов). 4 KPI-плитки
(всего/активные/замороженные/скоро истекают). Таблица из 9 колонок:
название, город, директор+телефон, ученики, филиалы, статус, месячная
выручка, дата истечения. Диалог создания института с блоком директора
(имя/телефон/пароль) и **4-шаговым индикатором прогресса** (схема →
миграция → директор → филиал) — честно: последние 3 шага **имитируются
таймером в 2 секунды**, реален только финальный успех/провал. Slug
генерируется транслитерацией кириллицы (включая қ ғ ҳ ў) с проверкой
занятости через 500мс debounce. Удаление института требует **вписать его
название**, при конфликте (409, есть активные ученики) — второй диалог
force-delete с точным числом того, что удалится.

**`/superadmin/analytics`** (134 строки). Только чтение: MRR/ARR (ARR —
это просто MRR×12), топ-8 институтов по выручке, ученики по городам.

**`/superadmin/logs`** (116 строк). Кросс-тенантный аудит — то же самое,
что `director/audit.tsx`, плюс колонка с названием учреждения.

**`/superadmin/settings`** (239 строк). Платформенные настройки: три
вкладки Общие/Безопасность/Бренд. **2FA-переключатель заведомо
disabled** с текстом «будет доступно в следующем обновлении» — видимая
недоделанная фича, не баг.

### director (директор учреждения — видит всё учреждение целиком)

**`/director` — Панель управления** (314 строк). 4 KPI (активные
ученики/выручка за месяц/прибыль/должники), график доход/расход за 14
дней, топ-5 учителей по посещаемости, лента аудита.

**`/director/students`** — тонкий реэкспорт `admin/students.tsx`,
директор и branch_admin видят один и тот же экран, разница только в
серверном скоупе данных.

**`/director/leads` — Заявки** (1131 строка). Воронка продаж —
5-колоночная kanban-доска с drag-and-drop (Новая → Связались → Пробный
урок → Записался → Отказался). Создание/редактирование лида, назначение
пробного урока, конвертация в ученика (+создание аккаунта родителя). На
мобиле — отдельная раскладка (одна колонка + переключатель, а не сжатые
5 колонок).

**`/director/staff` — Сотрудники** (411 строк). HR: найм, редактирование,
увольнение. Роль (director/branch_admin/teacher/support_teacher),
филиал, статус (active/vacation/fired/blocked), способ оплаты — процент
от стоимости курса (учителя) либо фиксированная зарплата (все
остальные).

**`/director/finance` — Финансы** (330 строк). Обзор денег по всему
учреждению за период: KPI доход/расход/прибыль/долг, разбивка по
филиалам, расходы по категориям, таблица кошельков всех учеников,
последние 12 платежей с возможностью **сторно**. Создание платежей здесь
**нет** — только у branch_admin.

**`/director/salaries` — Зарплаты** (548 строк). Месячная выплата
зарплат. Для каждого учителя параллельно запрашивается серверный расчёт;
если запрос падает — тихий откат на клиентский расчёт с явным жёлтым
бейджем «Оценка» (директор видит разницу между настоящей цифрой и
прикидкой).

**`/director/penalties` — Штрафы и бонусы** = компонент `NazoratPage`
(922 строки, общий с `/admin/control`). Три вкладки: Сегодня (чек-ин
учителей по дню), Преподаватели (месячный рейтинг: явка × 0.5 +
посещаемость × 0.3 + опоздания × 0.2), Штраф/Бонус (создание записей).

**`/director/daily-report` — Дневной отчёт** (696 строк, общий с
`/admin/daily-report`). Утренняя сводка одного дня: 5 KPI со стрелкой
дельты к вчера, разделы Финансы/Уроки/Посещаемость/Учителя/Новые лиды.
**Единственная страница с реальным экспортом** — Excel (5 листов) и PDF
(`window.print()`).

**`/director/analytics`** (222 строки). Только графики за 6 месяцев, без
фильтров и экспорта.

**`/director/audit` — Аудит** (117 строк). Лента «кто что изменил», без
пагинации.

**`/director/coins` — Монеты** (822 строки). Полная консоль экономики
геймификации: 5 вкладок Ученики/Настройки/Магазин/Заказы/Достижения.
Здесь настраивается вся экономика (сколько монет за что, пороги уровней,
товары магазина, достижения) — то, что видит `admin/coins.tsx` в
операционном, урезанном виде.

**`/director/messages`** — общий компонент `MessengerPanel` (390 строк),
внутренний чат.

**`/director/courses` — Курсы** (612 строк). Каталог программ обучения →
группы → состав группы, трёхуровневый drill-down через выезжающие
панели.

**`/director/branches` — Филиалы** (524 строки). Управление физическими
локациями и кабинетами, drag-and-drop переноса кабинета между филиалами.

**`/director/integrations` — Интеграции** (517 строк). Meta Pixel,
SMS (Eskiz.uz), LidPixel (генерация API-ключа для приёма лидов с сайта).

**`/director/settings` — Настройки** (362 строки). Бренд учреждения
(логотип, название), собственный профиль и пароль директора.

### branch_admin (портал `/admin` — операционка одного филиала)

**`/admin` — Сегодня** (250 строк). Уроки сегодня (макс. 7 + «Ещё N»),
последние платежи. Визуально отличается от остальных страниц — часть
использует сырые CSS-классы вместо стандартных shadcn-компонентов.

**`/admin/students`** (539 строк, общий с `/director/students`). Список
учеников с **серверной пагинацией и сортировкой** (50/страница —
специально прокомментировано в коде: клиентская сортировка отсортировала
бы только видимую страницу). Массовые действия (заморозить/разморозить)
с отменой через тост.

**`/admin/leads`** (1114 строк) — практически дубль `director/leads.tsx`,
тот же функционал, скоуп по филиалу.

**`/admin/accounts` — Аккаунты** (236 строк). Выдача/сброс паролей
учителям, ученикам, родителям. Автогенерация — слабый паттерн `edu` +
6 цифр, без подтверждения перед перезаписью.

**`/admin/quizzes`, `/admin/quiz-create`, `/admin/quiz-session/$id`** —
см. раздел «Квизы» ниже, общий с `/teacher`.

**`/admin/groups` — Группы** (796 строк). Создание групп, расписание
(7-дневная сетка), состав группы. Удаление — трёхстадийный флоу: отказ на
клиенте, если есть ученики → подтверждение → на 409 force-delete-диалог с
предупреждением, сколько платежей учителя пострадает.

**`/admin/schedule` — Расписание** (488 строк). Недельный вид всех
уроков, 7 колонок дней. Отмена (с обязательной причиной), перенос,
отметка «проведён».

**`/admin/finance` — Финансы** (768 строк). **Касса** — единственное
место, где реально принимаются платежи и создаются расходы. 5 вкладок:
Кошельки/Платежи/Должники/Расходы/История. Двойные клики защищены явно
(комментарий в коде: «второй клик — второй платёж»).

**`/admin/daily-report`, `/admin/analytics`** — тоньше директорских
аналогов, без фильтров.

**`/admin/coins`** (294 строки). Операционная часть монет — начисление,
заказы, лидерборд — без настройки экономики (та осталась у директора).

**`/admin/control`** — тот же `NazoratPage`, что и `/director/penalties`.

**`/admin/notifications`, `/admin/messages`** — инбокс уведомлений,
мессенджер.

### teacher

**`/teacher/groups`** (145 строк). Карточки своих групп с прогресс-баром

**`/teacher/attendance` — Посещаемость** (345 строк). **Эталонная

**`/teacher/homework` — Домашка** (310 строк). Создание ДЗ (на группу/на

## Сквозные подсистемы (общие для нескольких ролей)

### Биллинг за уроки — как это реально работает

Ключевое правило: **деньги списываются за КАЖДЫЙ проведённый урок**, а не
как абонемент разом за месяц. Ежедневная задача Celery в 23:00
(`daily_lesson_charge`, `backend/apps/finance/tasks.py`) проходит все
реально существующие уроки (`Lesson`, не запись в расписании) за сегодня
и списывает с каждого ученика цену одного урока — кроме `cancelled`,
`rescheduled` и посещаемости со статусом `excused`.

**Формула цены одного урока**
(`backend/apps/finance/services.py::calculate_lesson_price`):
```
цена_урока = месячная_цена_группы / (число дней недели по расписанию
              группы, попадающих на текущий месяц)
```
То есть если группа занимается по пн/ср/пт и в этом месяце 13 таких дней —
цена урока = месячная цена ÷ 13. Пересчитывается заново каждый месяц.

**Зарплата учителя** = процент (`Staff.salary_percent`) от суммы, реально
списанной с учеников его группы за период, минус штрафы, плюс бонусы
(`backend/apps/reports/services.py::calculate_teacher_salary`).

### Статусы и денежные типы (единый источник правды)

`backend/apps/core/definitions.py` (зеркало на фронте:
`src/lib/data/definitions.ts`, паритет между сторонами стережёт тест
`test_definitions_parity.py`) — это специально заведённый единственный
файл с определениями метрик, после инцидента, когда «активных учеников»
считали тремя разными способами в разных местах:

- **Посещаемость.** Присутствие = `present` + `late`. В знаменатель
  посещаемости попадают `present` + `late` + `absent` — `excused`
  сознательно исключён (иначе аккуратно оформленные справки портили бы
  метрику центру).
- **Статусы ученика.** Активен = `active` + `debtor`. Числится в центре
  (шире) = + `frozen`. Неактивен = `archived` / `graduate` / `expelled`.
- **Должник** определяется **только по балансу** (`balance < 0`), не по
  статусу `debtor` — статус может на короткое время отставать от баланса.
- **Деньги, куда движется кошелёк:** пополняют
  (`top_up`/`manual_top_up`/`discount`/`refund`), списывают
  (`charge`/`manual_charge`), не касаются кошелька вовсе (`expense` —
  расход организации).

### Геймификация (монеты)

Ученик получает монеты за посещение (10), опоздание (5), отличную оценку
(20), хорошую оценку (10), сданное ДЗ (15), верный ответ в квизе (5) —
всё настраиваемо директором на `/director/coins`. Монеты копятся в XP
(множитель настраивается), XP даёт уровни (пороги — редактируемая
таблица), есть серия дней подряд (streak) с бонусами на 7/30 дней.
Монеты тратятся в магазине (`/student/coins`) на товары с ограничением
по количеству покупок в неделю/месяц и минимальному уровню.

### Live-квизы (Kahoot-стиль)

Единственная функция с настоящим реалтаймом (сырой WebSocket, не
поллинг) и единственная с полностью анонимным доступом.

- **Создание** (`/admin/quiz-create`, `/teacher/quiz-create` — общий
  компонент `quiz-create-page.tsx`, 827 строк): вопросы, таймер на
  вопрос (5/10/20/30 сек), 4 варианта ответа с цветовой/фигурной
  кодировкой (▲◆●■, как в оригинальном Kahoot).
- **Два типа квиза:** `student` (для учеников, спрашивает только имя) и
  `lead` (для маркетинга — спрашивает имя+телефон+дату
  рождения+контакты родителя, результаты квиза при этом одновременно
  становятся отчётом по лидам).
- **Хостинг** (`/admin/quiz-session/$id`, `/teacher/quiz-session/$id`) —
  полноэкранный тёмный проекторный экран с кодом присоединения, живым
  списком участников, управлением вопросами.
- **Участие** — полностью вне авторизации: `/join` (ввод кода + имя) →
  `/play/$code` (сама игра). Личность хранится только в
  `sessionStorage`, никакого аккаунта не требуется.
- Соединение — сырой WebSocket `/ws/quiz/<code>/` с автопереподключением
  каждые 1.5 сек, если разрыв не был чистым.

### Внутренний чат

`MessengerPanel` (390 строк) — один общий компонент на все роли, где
есть пункт «Сообщения». Групповые/личные/широковещательные треды.

## Дизайн-система

- **Токены** (`src/styles.css`): `--primary` #c9481f (тёмно-оранжевый,
  «Spicy Paprika» — выбран владельцем лично через Coolors, синий/индиго
  исключён намеренно как «слишком похоже на конкурентов»), фон #f4f2ed
  (кремовый), сайдбар #2E282A (тёмно-серый). **`.dark`-блока в репозитории
  нет вообще** — тёмная тема была осознанно убрана как мёртвый код,
  переключатель темы есть в UI, но фактически не на что переключаться.
- **8 столпов UI** (полный список — в `CLAUDE.md` корня репозитория):
  микроанимации, типографика с иерархией, минимум 5 состояний на
  элемент, полноценные пустые состояния, обратная связь на каждое
  действие (тост через `apiErrorMessage`, не голая ошибка), детали для
  внимательного взгляда (детерминированный цвет аватара по имени),
  цвет только как сигнал (красный=опасность, зелёный=успех,
  жёлтый=предупреждение — никогда декоративно), отзывчивость под
  контекст (таблица → карточки на мобиле, `Sheet`/`Drawer` открываются
  снизу).
- **Опасные действия только через `ConfirmDialog`** — `window.confirm` в
  проекте не используется нигде, это жёсткое правило.
- **49 shadcn-примитивов** в `src/components/ui/`, плюс ~30 собственных
  переиспользуемых компонентов в `src/components/edu/` (см. список ниже).
- Единый `AppShell` на все 7 ролей — не три разных каркаса, как было
  раньше в истории проекта (раньше 5 из 7 ролей получали десктопный
  интерфейс даже на телефоне).

### Почему `teacher/attendance.tsx` — эталон

Явно названа в `CLAUDE.md` лучшей мобильной страницей проекта:
- **Ничего не спрятано в выпадающем списке.** Дата и урок — видимая
  горизонтально скроллящаяся лента, а не два `Select`, из-за которых
  раньше между открытием экрана и первым учеником стояло два скрытых
  меню.
- **Умный выбор урока по умолчанию** — открывается сразу на текущем или
  ближайшем уроке (урок считается «текущим» 90 минут от начала), не на
  первом уроке дня.
- Тёмная шапка группы с указанием, кто и когда уже отметил журнал.
- Кнопка «Отметить всех пришедшими» показывается **только пока ничего не
  отмечено** — счастливый путь в один тап.
- Неотмеченные ученики — пунктирная рамка, видно прогресс без чтения
  кнопок.
- Тач-цели 44px на мобиле, `StickyActionBar` учитывает нижнюю мобильную
  панель и safe-area iOS.
- Явно НЕ офлайн/оптимистичная — обычный await-запрос с тостом, без
  локальной очереди.

## Известные системные проблемы (не путать с новой веткой роли)

- **Два полных дубля страниц**: `director/leads.tsx` ≈
  `admin/leads.tsx` (1131/1114 строк — по сути одна страница,
  скопированная дважды) и `director/audit.tsx` ≈ `superadmin/logs.tsx`.
- **Смешанная i18n-дисциплина**: часть страниц берёт строки из общего
  словаря `useI18n()`, часть — инлайновые тернарники
  `lang === "uz" ? … : …`, часть (leads/nazorat/daily-report) держит
  свои локальные объекты `labels()`. Кое-где русский текст на самом деле
  ещё узбекский placeholder (`director/notifications`).
- **Два визуальных языка одновременно**: shadcn `Card`/`Table`
  большинства страниц против сырых CSS-классов на части
  `admin/index.tsx` и `admin/students.tsx`. `DailyReportPage` и
  `QuizSessionPage` вообще не используют `PageShell`.
- **Мобильная адаптация неравномерна**: у `leads` — своя раскладка под
  телефон, у крупных таблиц (`director/finance`, `salaries`,
  `admin/students`) — только `overflow-x-auto`, без превращения в
  карточки.
- **Единственный путь экспорта во всём приложении** — `DailyReportPage`
  (Excel/PDF). Больше нигде экспорта нет.
- Полный перечень внесённых и решённых инцидентов — в `CLAUDE.md`
  (раздел «ТЕКУЩИЙ СТАТУС И ОТКРЫТЫЕ ЗАДАЧИ»), включая уже закрытые:
  фантомные списания за уроки без реального занятия, двойное списание,
  дыры доступа по ролям, отсутствие бэкапов БД.

## Как этим документом пользоваться

Это слепок кода на конкретный момент, не спецификация будущего. Если
агент (например, планировщик или дизайнер) предлагает новую роль или
экран — этот файл даёт: (1) с чем реально придётся визуально соседствовать
(цвета/паттерны/компоненты), (2) какие права/скоупы уже существуют и как
их обычно комбинируют, (3) где в текущей системе уже есть недочёты,
которые новая работа не должна повторить (дубли страниц, разнобой i18n,
два визуальных языка). Не предполагайте, что что-то из перечисленного
идеально — часть явно помечена как техдолг.
